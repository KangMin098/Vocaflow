## 1. 기본값 = AUTO_CONTINUE

브랜치 선택은 [WORKTREE](../../docs/WORKTREE.md)의 연속성 정책을 따른다. 작업 단계·AI 교체·작은 수정만으로 새 브랜치나 PR을 만들지 않는다. `main`은 최종 기준, `local/integration`은 임시 통합이며 통합 검증 뒤 main으로 수렴한다. 코드 병합·원격 반영·DB 적용·서버 실행 버전은 각각 확인한다.

**실행 모드와 승인 범위를 구분한다.** 일반 개발은 LOCAL_FAST다. 요청→목표 확인→기획·설계→구현→영향 범위 테스트→제품 검증→커밋→로컬 통합을 한 작업으로 수행한다. 단계 변경이나 AI 교대에 TASK·브랜치·워크트리·세션·PR을 추가하지 않는다. 기존 TASK는 이어 쓰고 여러 세션의 공식 분담·추적에만 등록한다. 완료 기준은 요청한 제품 기능의 실제 달성이다.

- LOCAL_FAST: TASK 없는 일반 개발은 [WORKTREE §2](../../docs/WORKTREE.md)의 기존 잠금·검증 SHA 병합으로 로컬 main에 통합한다. 등록 작업만 중앙 `bin/local-integrate.mjs --task <ID>`를 사용한다. 작업별 push·PR·Actions 조회·CI 대기는 요구하지 않는다. 검증은 L1~L4의 영향 범위만 실행하고 HEAD·범위·환경이 같은 통과 증거를 재사용한다. 미실행·skip·차단된 브라우저 검증은 미검증으로 남기며 중단 지침을 준수한다.
- 백업은 중앙 `bin/backup.mjs`만 사용하고 중앙 설정의 하루 상한·복구 시점을 따른다. 백업 실패로 로컬 개발을 중단하지 않는다. Work Bridge는 기존 설계 요청 범위로 사용한다.
- 원격 동기화: 기존 `VocaflowMainSync` 예약 작업이 매일 22시 중앙 `bin/main-sync.mjs`를 실행한다. 미반영 커밋이 있을 때 하루 PR 하나로 묶어 GITHUB 모드의 필수 CI·범위 계약·safe-merge를 거친다. 네트워크·CI 실패는 로컬 개발을 막지 않는다. 원격 보호·필수 체크·중앙 백업 정책은 유지한다. 새 세션부터 공통 지침을 사용하며 이미 실행 중인 세션이 자동 갱신됐다고 간주하지 않는다.

사용자에게 매번 진행 여부를 묻지 않는다. 위 실행 모드에 맞춰 구현 → 검증 → 수정 → 문서화 → 커밋 → 해당 모드의 통합까지 이어서 한다.

**기존 데이터·DB 배포 통제를 유지하고 중대한 보안 변경을 명시한다.** 저위험 개발의 재승인과 혼동하지 않는다. 이번 정책 수정은 DB 배포 러너/승인 티켓 검증을 완화하지 않는다.

| 유형 | 범위 | 승인 요청에 붙일 것 |
|---|---|---|
| DB 변경 | 테이블 · 컬럼 · 제약 · 인덱스 · 마이그레이션 적용 · RPC · 함수 · 트리거 · RLS · 권한 · 데이터 의미를 바꾸는 대량 변환 | SQL 전문 · 영향 분석 · 되돌리기 |
| 데이터 삭제 | 기존 사용자 · 시험 · 학습 · 콘텐츠 데이터 삭제 · DROP · TRUNCATE · 대량 DELETE · 기록을 잃는 초기화 · 재적재 · 덮어쓰기 | 대상 · 범위 · 복구 방법 |
| 중대한 보안 변경 | 인증/권한 경계·브랜치 보호·필수 CI 완화, 인증정보 생성/회전/공유/외부 전송, 관리형 보안 정책 변경 | 정확한 범위 · 영향 · 복구 · 승인 증거. 이미 명시 승인된 범위는 재질문하지 않음 |

앱의 정상적인 INSERT · UPDATE · UPSERT, 기존 승인 범위의 데이터 처리, 실행별 소유권이 확인된 임시 테스트 데이터 정리는 승인 없이 한다.
승인을 기다리는 부분만 멈추고, 독립적인 나머지 작업은 계속한다.

## 2. 더 이상 묻지 않는 것

일반 개발 · 리팩터링 · UI/UX · 코드 리뷰 · 테스트 · 오류 수정 · 문서 정합성 · 커밋 · push · PR 생성 · base 변경 · 필수 CI 실행 · 안전 조건을 충족한 main 병합 · AI 역할 검수 · 기존 계약의 콘텐츠 처리.
**파일 30개 이상**은 승인 조건이 아니라 **추가 검증 조건**이다 — PR 본문에 `## 검증` 절(실행한 검증과 결과)을 쓰고, 커밋을 쪼개 우회하지 않는다.

## 3. 원격 동기화 PR 흐름

로컬 통합 완료 → 일일 미반영 변경 묶음 → 동기화 브랜치 push → PR → 필수 CI → 실패 원인 분석 · 허용 범위 수정 · 관련 재검증 → `safe-merge.mjs` → 원격 main 병합. 일반 작업마다 이 흐름을 반복하지 않는다.

`node agents/scripts/safe-merge.mjs <PR> --scope-file <계약.json> [--wait] [--dry-run]`이 병합 직전에 확인한다. 계약은 승인 작업의 정확한 경로와 HEAD/base SHA·예상 커밋 수를 담으며 없거나 불일치하면 원격 병합하지 않는다. 예시/진단은 [개발환경 감사](../../docs/agents/development-autonomy-audit.md).

1. PR 열림 · MERGEABLE · **base = main**(종속 PR 은 앞 PR 병합 뒤 base 가 main 으로 바뀌고 CI 가 다시 돈 다음에만).
   범위 계약의 HEAD/base SHA·전체 변경 경로·커밋 수도 일치해야 한다. #318처럼 CI가 성공한24커밋160파일을 승인15파일의 작업으로 병합하지 않는다. 병합 직전 HEAD/base/커밋 수를 다시 대조한다.
2. **필수 체크 전부**(pr-automation.json `required_checks`)가 최신 HEAD 에서 SUCCESS — 하나라도 없으면(누락) · SKIPPED 뿐이면 · 대기면 병합 안 함.
3. **DB 변경 승인 증거 = 개발 DB 적용 이력** — `supabase/migrations/` 를 바꾼 PR 은 파일마다 개발 DB `supabase_migrations.schema_migrations` 의 statements sha256 이 PR HEAD 본문 sha256 과 같아야 한다. 적용은 사용자 승인 + DB 쓰기 훅을 거쳐서만 생기므로 PR 작성자가 꾸밀 수 없다. **PR 본문 문자열은 증거가 아니다**(이 머신은 에이전트와 사용자가 같은 GitHub 계정을 써서 작성자를 가릴 수 없다). 미적용 · 적용 뒤 수정 · 이력 조회 실패(SUPABASE_ACCESS_TOKEN 없음)는 병합 안 함. `_pending_` 제안본은 적용되지 않으므로 메모로만 남긴다.
4. **데이터 삭제** — 삭제 구문(DROP TABLE · TRUNCATE · DELETE FROM · DROP COLUMN)이 있는 마이그레이션은 종류를 밝히고 같은 적용 이력 증거가 필요하다. 마이그레이션 파일 삭제는 승인 대상이라 막는다.
5. **30파일 이상** → 본문 `## 검증` 절.
6. 필수 체크가 **이 HEAD** 에서 · **마지막 base 변경 뒤에** 성공했는지(check-runs · timeline). 7. 병합 직전 HEAD · base 를 다시 읽어 비교하고, 병합은 `gh pr merge --match-head-commit <확인한 SHA>` — 확인 뒤 새 커밋이 들어오면 GitHub 이 거부한다(SHA 변경 = 재검증).

## 4. 자동 main 병합 활성화(2026-10-11 켜짐)

**현재 상태: 켜짐** — origin/main 의 `merge.auto_merge_enabled = true`(PR #210 · 사용자 커밋 `0b0d01148` · 2026-10-11 main 병합). safe-merge 는 이 값을 **origin/main 에서만** 읽는다. 켜기 전에 확인한 조건:

1. PR 필수 `e2e` 가 실제로 돈다 — 2026-10-11 전에는 시크릿이 없으면 건너뛰고도 SUCCESS 였다(가짜 통과). 이제 PR 필수 `e2e` 는 **격리 실행**(러너 안 로컬 Supabase + 저장소 마이그레이션 실제 적용 + next start + Playwright + DB 단언 · 공유 DB · 시크릿 불필요)이고, 공유 개발 DB E2E 는 `e2e-shared-dev`(main push · 수동 실행만 · 시크릿 필요)로 분리했다.
2. 모든 base 의 PR 에서 필수 CI 가 돈다 — 전에는 `pull_request: branches: [main]` 이라 종속 PR(#206 · #207 · #209)에 CI 가 없었다. 필터를 풀었다.
3. (선택) 공유 개발 DB 통합 E2E(`e2e-shared-dev`)에 쓸 저장소 시크릿 — PR 필수 조건은 아니다. 비밀값은 에이전트가 외부에 올리지 않는다.
4. main 보호 — 2026-10-11 설정: branch protection(필수 체크 8 · strict · 관리자 포함 · PR 필수 · force push/삭제 금지) + Ruleset `Vocaflow-main-protection`(active · 우회 계정 없음). 확인 `gh api repos/KangMin098/Vocaflow/branches/main/protection` · `gh api repos/KangMin098/Vocaflow/rulesets`.

활성화 뒤 첫 적용: #205 → #206 → #207 → #209 를 safe-merge 로 순차 병합(2026-10-11 · DB 승인 증거 = 개발 DB 적용 이력 해시 일치). 다시 끄면(값 false) 꺼져 있는 동안 `safe-merge.mjs` 는 **어떤 경로로도 병합하지 않는다**(`--dry-run` 판정만 · 자동/수동 구분 없음). 켜는 길은 이 값을 바꾸는 PR 하나뿐이고, 그 PR 도 보호된 main 의 필수 CI 를 거친다. 켜진 뒤에는 게이트를 통과한 PR 을 묻지 않고 병합한다.

## 5. 실패 · 예외

| 상황 | 할 일 |
|---|---|
| 코드 오류 · 테스트 실패 | 원인 분석 → 수정 → 재검증 |
| CI 미실행 | 실행 조건 복구(트리거 · base) |
| PR 충돌 | 허용 범위에서 안전하게 해결(force push 금지) |
| 교육적 근거 부족 | 검증 전 상태 유지 |
| DB 변경 필요 | SQL · 영향 분석 작성 → 승인 요청 |
| 데이터 삭제 필요 | 대상 · 범위 · 복구 방법 → 승인 요청 |
| 비밀정보 · 권한 우회 · 보안 위험 | 멈추고 보호장치 유지 |
| 고칠 수 없는 외부 장애 | blocker 보고 |

테스트 실패나 권한 부족을 사용자 승인으로 우회하지 않는다.

## 6. AI 역할 위임

단일 AI가 수행 가능한 작업은 기획부터 구현·검증·통합까지 연속 수행한다. 별도 AI 검토·인수인계는 실제 필요하거나 명시된 독립 검토 계약이 있을 때만 기존 기능으로 수행한다. 모든 커밋·완료 시점에 자동 호출하지 않는다. 실제 사람의 수행 데이터나 법적으로 필요한 동의를 AI가 대신 만들거나 충족했다고 주장하지 않는다.

## 7. 보고

작업 단계·커밋·로컬 통합마다 승인을 요청하지 않는다. 최종 보고는 ① 실제 구현·개선된 기능 ② 테스트·검증·통합 결과 ③ 미완료 항목·실제 차단 사항만 쓴다. 기능 계약·제품 방향이 바뀐 정본만 갱신하며 별도 관리 보고서를 만들지 않는다.

## 8. 적용 확인

- `node agents/scripts/check.mjs` D11 — 정책 파일 존재 · JSON 유효 · AGENTS.md 정책 줄 버전 = JSON 버전 · DECISIONS 이력.
- 세션 시작 훅(`handoff-inject.mjs` — 두 AI 공통)은 워크트리와 origin/main의 정책 버전 차이를 알린다. 일반 개발 절차는 중앙 `development_policy`가 우선하며, 이 안내만으로 활성·미커밋 작업에 원격 병합이나 공간 정리를 강제하지 않는다.
- **이미 실행 중인 세션은 정책을 다시 읽지 않는다** — AGENTS.md · 훅은 세션 시작에 한 번 읽힌다. 정책이 바뀌면 그 세션을 다시 시작하거나 정본을 직접 다시 읽게 한다.
