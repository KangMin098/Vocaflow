1. **납품 완료 주문의 받은 자료를 못 연다.** dcp-learning.pglite.test의 새 첫 시험은 기존 factory_order_transition으로 requested→stock_search→delivered(3문항 모두 실제 납품) 후 열기를 검사한다. 실제 결과는 false다. 원인은 생산중 주문만 true인 factory_lineage_personal_current를 학습 열기에 그대로 쓴 것이다. 그 기존 함수의 생산/신규 링크 안전 계약을 완화하지 말고, 학습용 현재성 판정에서 현재 Workspace/goal/plan/line/spec는 유지하면서 과거 주문의 정상 delivered/partial 상태로 이미 받은 자료가 막히지 않게 한다. failed/철회/구 판본을 허용하라는 뜻이 아니다. 완료 주문에서도 열기/실제 채점 성공, 구 goal/plan과 닫힌 Workspace는 계속 차단한다. 동일 제출 재전송의 역사적 결과 반환도 유지한다.

3. **수행 결속을 더 강하게 검증.** SQL factory_dcp_attempt.csat_attempt_id는 실제 csat_item_attempts.id UUID에 FK로 묶고, 실제 grade_dcp_item 반환 후 그 행이 호출 학습자/그 DCP 문항/반환 정오에 맞는지 확인한다. 가짜·다른 사용자·다른 문항 id 또는 누락 정오는 트랜잭션을 실패시켜 저장하지 않는다. 신규 표에 기존 supply_writer_guard를 추가하고 실제 RPC가 그 writer 설정을 하게 한다(service_role SELECT만 남긴 기존 회수는 유지). 목표→계획 자문 키와 Workspace/납품/문항 등 필요한 행 잠금을 실제 현재성 조회 전에 얻어 승인된 writer와 직렬화한다. 1C의 잠금과 권한을 재사용하되 private helper나 원본 RPC 실행권을 학습자에게 열지 않는다. 실제 두 연결 동시성은 미실행으로 정확히 둔다. 직접 쓰기 차단·실패 롤백·재전송을 실제 PGlite로 시험한다.
4. **미구현 계약을 이번 단계에서 완료.** analytics 진입/선택·제출/복귀를 `lib/analytics/events.ts` 계약과 함께 연결한다(숫자/boolean/closed enum만, id/본문 없음). 맞는 기존 이벤트를 재사용할 수 있으면 그렇게 하고, 새 이벤트 CHECK SQL이 필요하면 pending SQL에만 작성한다.
