# 원천 수집·판정 기준설계 — 채택분만 적재하고, 제외는 묘비로 기억한다

> 2026-09-23 사용자 결정. 적용 대상: ACP 수집기 · `library_articles` · 내용 판정 드레인 · 적격 판정 캐시 · Admin.
> 배경 실측은 전부 이 문서 안에 날짜와 함께 있다. 수치를 인용하려면 여기가 아니라 DB 에 다시 묻는다.
> 파이프라인 전체 그림은 [LIBRARY_PIPELINE](./LIBRARY_PIPELINE.md).

## 왜 바꾸는가 — 실측된 결함 셋 (2026-09-23)

**① 「이미 봤다」는 기억이 본문 저장소 자체다.**
`scripts/acp/collect-daily.mjs` 는 매 실행마다 `library_articles` **전량**(109,047행)을 1,000행씩
110회 읽어 `source_url` · `source_id` 집합을 만들고, 그 집합에 없는 것만 새 것으로 친다.
즉 **반려한 글의 행을 지우는 순간 다시 GET 하고 다시 판정한다.** 그래서 내용 반려 20,275편(본문 85 MB)을
「잊지 않기 위해」 영구 보관하고 있다 — 쓰지 않을 본문을 기억 용도로 쥐고 있는 셈이다.

**② 중복 검출이 GET 뒤에 온다.**
수집기에 `content_hash` 대조가 없다. 같은 본문이 다른 주소로 오면 **받아서 저장한 뒤에야** 안다
(중복 해시 115건). 주소·`source_id` 대조만으로는 못 막는다.

**③ 비용이 재고에 비례해 늘어난다.**
전량 스캔은 재고가 늘수록 비싸진다. 이미 110 왕복이고, 과거에 PostgREST 1,000행 절단 때문에
집합이 **조용히 잘려** 900여 편을 다시 GET 한 사고가 있었다(스크립트 주석 2026-08-30).

## 원칙 넷

1. **본문은 채택된 것만 보관한다.** `library_articles` 에 들어간다는 것은 「내용 판정을 통과했다」는 뜻이다.
2. **제외는 잊지 않는다.** 본문 없이, 다시 판단하지 않을 만큼의 **최소 정보**만 묘비로 남긴다.
3. **재확인은 신원으로 막는다.** GET **전에** 주소·`source_id` 로, GET **후에** 본문 해시로 건다.
4. **제외에도 문이 있다.** 기계 규칙이 바뀌면 기계 제외만 다시 연다. 내용 판정은 사람·LLM 의 판단이므로
   자동으로 다시 열지 않는다 — 여는 것은 언제나 명시적 행위다.

## 흐름

```
목록 발견
   │
   ├─[① 신원 조회: source_id · url_hash]──▶ 묘비에 있음 ──▶ 끝 (GET 하지 않는다)
   │  새 것
   ▼
  GET
   │
   ├─[② 본문 해시 조회: content_hash]──▶ 묘비/보유에 있음 ──▶ 묘비에 주소만 덧대고 끝
   │  새 본문
   ▼
 staging (본문을 임시로 든다)
   │
   ├─[③ 기계 게이트: 저작권·안전·형식·규칙]──▶ 제외 ──▶ 묘비(stage=machine) + 본문 폐기
   │  통과
   ▼
 staging
   │
   ├─[④ 내용 판정 (LLM 드레인)]──▶ 제외 ──▶ 묘비(stage=content) + 본문 폐기
   │  채택
   ▼
 library_articles 적재 (본문 포함) ──▶ 이후 발췌·문항·조판
```

⚠️ **길이는 이 흐름 어디에도 없다.** 원문이 지문 창보다 긴 것은 정상이고, 자르는 일은 교재 생성 단계가
유형별 창으로 한다(2026-09-23 결정 · `compose-unit.itemWordSpec`). 길이로 원문을 제외하지 않는다.

## 테이블

### A. `library_source_exclusions` — 묘비 (본문 없음)

| 열 | 뜻 |
|---|---|
| `source` · `source_id` | 신원. **GET 전 조회 키** |
| `url_hash` | 정규화 주소의 sha256. `source_id` 가 없는 소스용 |
| `content_hash` | 본문 sha256. **GET 후 조회 키** |
| `scope` | `identity` = 이 주소/이 글은 다시 보지 않는다 · `content` = 이 본문만. 내용이 바뀌면 다시 본다 |
| `stage` | `machine` · `content` |
| `reason` | 사유 코드. **기존 blocker 어휘를 그대로 쓴다**(새 어휘를 만들지 않는다) |
| `rules_version` · `codes_version` | 기계 제외를 다시 열 때의 기준 |
| `title` | 사람이 읽을 짧은 제목(운영 디버깅 전용 · 길이 제한) |
| `decided_at` · `reopened_at` | |

**본문·저자·발행일·분석값·CEFR·어수는 담지 않는다.** 담기 시작하면 두 번째 본문 저장소가 된다.
행당 200 바이트 안팎 → 23,283행이 **약 5 MB**. 지금 92 MB 가 하는 일을 대신한다.

`scope` 를 나누는 이유: 저작권·안전 제외는 본문이 고쳐져도 유효하지만(`identity`),
「이 판본이 조각글이다」는 본문이 바뀌면 다시 봐야 한다(`content`).

### B. `library_article_staging` — 판정 대기 본문

판정이 끝날 때까지만 본문을 든다. 결정 나면 즉시 승격(A→`library_articles`) 또는 폐기(→묘비).
**TTL 이 있어야 한다** — 넘긴 것이 쌓이면 경보한다. 방치된 후보가 조용히 늘어나는 것이
지금 `unjudged` 8,814편이 생긴 경로다.

### C. `library_articles` — 채택분만

스키마는 지금 그대로. 바뀌는 것은 **불변식**이다: 여기 있는 모든 행은 내용 판정을 통과했다.
`csat_fit.gate.verdict='reject'` 인 행이 존재하지 않는다.

## 조회 비용

| | 지금 | 기준설계 |
|---|---|---|
| 수집 1회의 보유 목록 | 전량 110 왕복 (재고에 비례해 증가) | 후보 해시 `IN` 조회 1~2회 |
| 중복 발견 시점 | GET·저장 **후** | GET **전**(주소·id) / GET 직후(해시) |
| 반려 본문 | 영구 보관해야 함 | 폐기 가능 |

## 제외를 다시 여는 문

- `rules_version` 이 오르면 **`stage='machine'` 묘비만** 재개방 후보가 된다.
- `stage='content'` 는 자동으로 열리지 않는다. 운영자가 **사유 코드 단위로** 연다
  (예: 「`reference` 판정을 다시 본다」).
- 여는 것은 묘비를 지우는 것이 아니라 `reopened_at` 을 찍는 것이다 — 왜 다시 봤는지가 남아야 한다.

## 못박을 불변식 (회귀)

1. `library_articles` 에 `gate.verdict='reject'` 인 행이 0이다.
2. 묘비 테이블에 본문 성격의 열이 없다(스키마로 보장 — 길이 상한).
3. 수집기는 **GET 전에** 묘비를 조회한다. 회귀: 이미 제외된 주소를 목록에 넣고 **GET 호출 0회**를 확인.
4. 같은 `content_hash` 가 `library_articles` 에 두 번 적재되지 않는다.
5. 묘비 조회는 재고 크기와 무관하게 상수 회 왕복이다(전량 스캔 금지).

## 이행 — 되돌릴 수 있는 순서로

1. **묘비 채우기(읽기 전용 산출 → 검토 → 적재)**: 확정 제외분 23,283행에서 묘비를 만든다. 본문은 **그대로 둔다.**
2. **수집기를 묘비 조회로 전환**: 전량 스캔을 묘비 + 보유 해시 조회로 바꾼다. 이 시점까지 되돌릴 수 있다.
3. **실측 확인**: 수집을 1회 돌려 GET 횟수·중복 수·소요가 실제로 줄었는지 잰다. 안 줄면 설계가 틀린 것이다.
4. **그 뒤에야 본문 폐기**: 되돌릴 수 없다. **사용자 승인 + 백업 필수.**

⚠️ 1~3 은 되돌릴 수 있고 4 만 되돌릴 수 없다. **4를 앞당기지 않는다.**

## 보관 축 — 게시 가능 여부와 다른 축이다 (2026-09-23 결정 · 사용자 승인)

`decide()` 는 「지금 이 원문을 **그대로 게시할 수 있는가**」만 답한다. 그 답이 `false` 라고
버릴 것이라는 뜻이 아니다. 두 뜻을 한 칸으로 읽었더니 **「확보한 원문 전량에 보관 판정이 있느냐」는
물음에 답할 수가 없었다** — 게시 불가와 미보관이 구별되지 않았기 때문이다.

그래서 보관을 **파생 축**으로 분리했다(`gate-rules.retentionOf`). 컬럼에 저장하지 않는다 —
저장하면 규칙을 고쳐도 데이터가 안 따라온다(같은 파일 `RULES_VERSION` 주석의 2026-09-06 사고).

| 값 | 언제 | 근거 |
|---|---|---|
| `keep-pending-extraction` | `purpose:'raw'` | **클래스 규칙.** 자르지 않은 논문 전문이라 판정을 붙여도 게시가 열리지 않는다. 여는 것은 판정이 아니라 추출(`plos-extract`)이고, 개별 판정은 **추출된 발췌**에 붙는다 |
| `keep` | 내용 판정 `use`·`narrative` | 본문을 읽고 남기기로 했다 |
| `discard` | 내용 판정 `reject` | 본문을 읽고 버리기로 했다 |
| `undecided` | 그 외 | **0이 아니면 관리 구멍** |

**실측 2026-09-23** — 미판정 40,174편의 내역:

| 집합 | 편수 | 보관 축 | 왜 판정 대상이 아닌가 |
|---|---|---|---|
| `plos` · `purpose:'raw'` | **31,220** | `keep-pending-extraction` | 전량이 예외 없이 `blockedBy:'oversize-raw'` · `publishable:false` 하나였다. `gate-article-export` 의 스코프 경로가 이 집합을 **일부러 제외**한다(문항이 이미 붙은 raw 만 예외) |
| B 버킷 판정분 | 8,033 | `keep`/`discard` | 이번 드레인이 전량 판정 |
| `original` · `status:'queued'` | 888 | `undecided` | queued 는 수집이 안 끝난 상태다. export 가 `ready`/`published` 만 본다 — ready 로 올라오면 정규 드레인이 집는다 |
| 기타 archived·queued | 약 90 | `undecided` | 위와 같다 |

**A 버킷이 빈 파일 1,736개를 낸 이유가 이것이다** — 추출기가 고장난 것이 아니라 조건에 맞는 행이
없었다. 1,739청크 중 내용이 있는 것은 3개(18편, 문항이 붙은 raw)뿐이었다. 빈 청크를 보고
「추출 실패」로 읽으면 없는 고장을 고치게 된다.

감사(`csat-sources-audit`)가 이 축을 **확보 전량**에 대해 센다(조판 후보 ready/published 만이
아니라 archived·queued 포함 — 후보만 세면 집계 밖으로 빠진다). `undecided` 는 `출처/상태` 별로
쪼개 찍는다: 합계만 보면 어느 파이프라인이 구멍인지 알 수 없다.

## 아직 정해지지 않은 것 — 결정이 필요하다

- **staging 을 새 테이블로 둘지, `library_articles.status='staged'` 로 둘지.**
  새 테이블은 불변식 ①이 깨끗해지지만 적재 경로가 둘이 된다. 상태값은 반대다.
- **CEFR 밴드 초과 55,235편을 어느 쪽으로 볼지.** 지금은 기계 축에서 막힌다. 그런데 밴드 적합은
  글의 V-Level 재계산으로 바뀔 수 있으므로, 묘비(제외)로 볼지 staging 보류로 볼지가 갈린다.
  **이 수가 가장 크므로 이 결정이 저장량을 가장 크게 좌우한다.**
- **아카이브 2,928편의 지위** — 제외인가, 한때 채택이었다가 내린 것인가.
