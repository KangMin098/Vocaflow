### 변이 검사 — 회귀가 실제로 잡는가

새 회귀는 값의 모양이 아니라 **두 화면이 같은 출처를 보는가**를 잠근다. 셋 다 잡혔다:

| 변이 | 잡혔나 | 무엇이 잡았나 |
|---|---|---|
| ① 옛 버그 되살리기(L2 를 다시 `csat_coverage()` 로) | ✓ | 라벨 검사 — `'교재 문항' 없음` |
| ② **라벨만 새것으로 두고 수는 기출** | ✓ | 수 검사 — `expected 802 to be 4` |
| ③ L2 를 푸는 명령 제거 | ✓ | 명령 검사 — `L2 명령이 없다` |

②가 중요하다. 라벨만 검사하면 이름을 바꾸고 출처는 틀린 채로 통과한다 —
**이번에 고친 버그가 정확히 그 모양이었다**(2026-09-13 에 한쪽만 고쳤다).

## 4. 미착수 — 그리고 이 감사가 틀렸던 곳

### 4-1. 이 감사가 두 번 틀렸다 (둘 다 진단서에서 정정함)

| 무엇 | 왜 틀렸나 |
|---|---|
| ④ 소재를 「통과」로 적었다 → **「못 잼」이 맞다** | 눈금(4/4)만 읽고 `state()` 가 주입하는 「못 잼」을 셈에 안 넣었다. 화면을 본 쪽이 옳았다 |
| ⑦ L3 를 「19/19」로 적었다 → **「16/19」가 맞다** | SQL `jsonb is not null` 은 **JSON 의 `null` 을 「있음」으로 센다.** 앱은 JS 로 읽어 3건을 없는 것으로 센다 |

두 번째는 이 저장소가 반복해 겪는 함정이다 — **「없는 것과 0(과 JSON null)을 가른다」**.
SQL 로 앱 수치를 검증할 때는 `jsonb_typeof(x) <> 'null'` 을 함께 봐야 한다.
