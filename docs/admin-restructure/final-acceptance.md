# 관리자 재구조화 최종 수용

2026-10-20 · 사용자 지시 ‘최종 목표 까지 무조건 진행해줘’의 관리자 메뉴·화면·프로세스 재구조화 범위를 완료했다. 이전 설계/시점별 보류 기록은 이 문서와 실제 중앙 로컬 통합 증거를 기준으로 읽는다. 실제 학습 효과·생산/발행 실적은 이 작업의 완료 기준에 포함하지 않는다.

## 기존과 최종 구성

| 항목 | 기존 상태 | 최종 상태·검증 |
|---|---|---|
| 메뉴와 하위 공간 | 직접 메뉴 30개와 펼침 자식 28개가 서로 다른 층으로 섞임 | 업무별 상위 7개·하위 22개. 원래 89페이지의 소속을 빠짐없이 정리 |
| 화면·프로세스 | 대상/기준/작업 상태와 목록 복귀가 분산 | 기존 엔진을 유지하며 도서 3보기·검수 복귀, 기출 목록 맥락, 연구 중복 내비, 학습자 계획/수행/공급/진단과 제품 적용 추적을 연결 |
| 공용 주문 계보 | 개별 문자열과 미결 계약·미설치 DB | 정본 해시·개인 수요 결속·비소모성 배분·개정·철회·전체 본문 멱등 계약과 DB/API/조회 화면 연결 |

## 마지막 실제 실행

영구 하네스는 `scripts/db/factory-i1/d3-live-check.mts`다. 기본 비활성화이며 `VF_D3_LIVE_APPROVED=1`과 `--run-owned-fixture`가 모두 필요하고 CI는 거절한다. opt-in 문자열은 사용자 승인을 대신하지 않는다. 실행 전에 해당 사용자 지시와 계정/원장 보존 범위를 확인한다. 이번 실행은 소유 marker `f0db1c87-800d-41ad-aa10-4ef651b60cf4` 한 개를 사용했다.

| 실제 확인 | 결과 |
|---|---|
| 우회 없는 비밀번호 로그인과 관리자 진입 | 통과 |
| 계획 저장 RPC→수요 등록→개인 주문→공용 등록/연결 | 통과 |
| 같은 UUID 재전송·새 UUID 별칭·같은 UUID의 본문 변조 거절 | 통과 |
| 개정으로 이전 링크 보존·새 판 현재 연결 | 실제 API/화면 통과 |
| 철회 및 철회 재전송 | 실제 API/화면 통과 |
| 개인 계획 버전 변경으로 기존 연결의 현재성 해제 | 실제 API/화면 통과 |
| 네 상태의 실제 관리자 페이지 | 현재/이전 판/철회/개인 변경 모두 표시. 1440×900, 키보드·44px·가로 넘침·계보 패널 axe 확인 |
| 실제 인증 메뉴 목적지 | 중복 제거한 23 URL 모두 HTTP 200. 로그인 페이지로 잘못 이동한 목적지 0 |
| 브라우저 실행 오류 | 0 |
| 실행 결과 | 35개 체크 통과, 생략 0 |

고정 렌더만으로 실제 양성 경로를 대신하지 않았다. 기존 `ProductOrderLineageView`가 실제 API/DB의 행을 읽는 관리자 페이지에서 네 번 캡처했다. 같은 실행에서 모든 89 상세 URL을 브라우저로 열었다는 뜻은 아니다. 현재 구현 전용 `node scripts/admin/v21-audit.mjs`는 89/89·7/22·오류 0을 확인했고, 내비 회귀 2파일 9개와 live 소유권/정리 회귀 14개도 통과했다.

옛 `submenu-audit.mjs`는 제안 당시의 v1 소속과 원본 파일 해시를 보존하는 감사다. 구현 이후의 소스 변경을 stale로 거절하므로 현행 수용 검사로 사용하지 않는다. 원본 스냅샷을 현재 값으로 덮어써 감사 결과를 통과시키지 않았다. 이력은 유지하고 현재 구현은 `v21-audit.mjs`로 검증한다.

## 검증 데이터와 권한 정리

기존 계정의 비밀번호나 역할은 변경하지 않았다. 이번 실행이 새로 만든 합성 계정 하나를 검증 중에만 admin으로 사용했다. 공유 DB의 추가 전용 원장은 삭제하거나 트리거를 우회하지 않았다.

| 종료 후 직접 DB 읽기로 재확인한 대상 | 상태 |
|---|---|
| 자체 공용 주문 3판/개인 링크 3개 | 합성 이력 보존. 현재 유효 공용 주문 0 |
| 개인 주문 | `failed` — 생산하지 않고 검증 종료 |
| 자체 Workspace | `closed` |
| 계정 | `user`로 권한 제거 + `suspended` + 인증 차단 |
| 종료 후 같은 세션의 관리자 API | HTTP 401 |
| 개인 납품 | 0 |
| 전후 DB 체크포인트 | 같은 run의 before/after 2개 존재 |

정리 작업은 각각 실행하며, 주문 철회/Workspace 닫기 실패가 관리자 권한 회수와 계정 정지를 막지 않는다. 정확한 계정 ID·합성 marker·run·제품 접두사를 모두 확인하는 회귀가 이를 지킨다. 실패를 성공으로 바꾸거나 전역 selftest 조건으로 남의 데이터를 지우지 않는다. 실제 운영 주문으로 사용하는 계정이 아니므로 이 기록은 생산·납품·실제 학습자 효과의 증거가 아니다.

로컬 원증거: `.agent-logs/d3-live/f0db1c87-800d-41ad-aa10-4ef651b60cf4/`의 `proof.json`, `postverify.json`, 네 상태 PNG. 인증 키·비밀번호·세션 파일은 산출물에 저장하지 않았다. 최종 리뷰에서 이 합성 계정의 도메인이 기존 통계 제외 규칙과 달라 가입자가 1명 늘어난 것처럼 집계되는 결함을 발견했다. 정확한 UUID·소유 marker가 일치하는 이 계정 하나만 기존 합성 도메인으로 정정했고 역할·정지·인증 차단 유지와 전후 체크포인트를 확인했다(`domain-repair.json`). 그 뒤 `pnpm docs:db-stats`를 다시 실행해 실가입자 1명으로 집계됨을 확인했다. 후속 회귀는 실제 통계 생성기와 앱의 합성 도메인 목록을 읽어 재발을 막는다. 설치 시점에 보고한 advisor 안내는 [DB 적용 기록](product-order-lineage-deployment.md)에 그대로 남기며 추가 DDL이나 성능 정책 변경은 하지 않았다.

## 재실행과 실패 복구

사용자 승인이 있는 실제 검증에서만 다음처럼 실행한다. 명령의 `.env` 값은 출력하지 않는다. 연결은 동일 개발 프로젝트의 명시적 5432 session 연결과 검증된 CA를 사용한다.

```powershell
$env:VF_D3_LIVE_APPROVED = '1'
node --tls-max-v1.2 --env-file=apps/web/.env.local --env-file=<DB 연결값이 있는 .env 파일> node_modules/tsx/dist/cli.mjs --tsconfig apps/web/scripts/tsconfig.harness.json scripts/db/factory-i1/d3-live-check.mts --run-owned-fixture --base http://localhost:3001 --deps <pg 설치 폴더> --ca <Supabase CA 파일>
```

실행마다 새 run/계정을 만들므로 기존 검증을 멱등 재사용하는 명령은 아니다. 중단되면 해당 run의 로컬 `ownership.json`과 실제 사용자 metadata를 대조한 뒤 **그 run의** 공용 주문 철회·개인 주문 실패 종료·Workspace 닫기·역할 제거·계정 차단을 각각 재확인한다. 이미 끝난 이력은 삭제하지 않으며, 기존 run 정리를 확인하기 전에 새 run을 무작정 반복하지 않는다.

최종 리뷰 후 하네스는 등록 요청 전에 제품 ID·판·해시·요청 UUID와 전체 요청 본문을 디스크에 저장한다. 응답 유실 시에는 같은 본문/UUID를 재전송해 지연된 원요청까지 멱등 결속한 뒤, 실제 등록자와 원장 식별값·현재성을 직접 읽어 자체 현재 판만 철회한다. 원장 불일치나 조회/재전송 실패는 정리 실패로 남기고 권한 회수·차단은 계속한다. 이 보완은 commit 후 응답 유실·요청 미도달/지연·개정 응답 유실·디스크 실패·소유 불일치 주입 회귀로 확인했다. 실제 35체크 실행은 보완 전 소스의 정상 응답 경로였으며 원본 해시와 화면 증거를 보존했다. 보완 후 공유 DB live 실행을 반복한 것으로 보고하지 않는다.

계획 저장과 개인 주문 생성도 호출 전에 전체 RPC 인자(기준 시각 포함)와 UUID를 같은 원장에 보존한다. 응답 유실로 ID가 비어 있으면 정리 단계에서 동일 요청을 재전송해 ID를 회수한 뒤 주문/Workspace를 종료한다. 계정 생성도 지원되는 사전 지정 UUID와 합성 marker를 먼저 저장하되 비밀번호는 저장하지 않는다. 소유권 Auth API가 일시 실패하면 직접 DB의 동일 UUID·run·synthetic marker를 확인해 역할 회수/차단을 계속한다. 응답된 소유권이 다른 경우는 fallback으로 덮지 않고 거절하며, 두 조회가 모두 실패하면 미완료로 남긴다.
