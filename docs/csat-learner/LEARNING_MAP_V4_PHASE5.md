## 2. 빠져 있던 것 → 고친 것

1. **바로잡기 · 적용 단계에 활동 링크가 없었다** — 계획의 「활동 시작」은 확인 · 다시 확인에만 생겼다. → Workspace 가 단계별 대상(`stageItems`: 막힌 확인 문항 · 연습 화면 `?item=` 전이 문항)을 내고, 계획이 아직 안 한 것 하나를 고른다.
2. **확정(REPAIR) 요구 안에서 단계가 「바로잡기」에 고정** — 정본 quantity_policy 순서(바로잡기 → 전이 2지문 → 재확인)로 수행에 따라 넘어가게(`plan.stageNow`). 문항이 없는 단계는 건너뛰고 「준비 중」으로 보인다. 적용 계획량 = 정본 「전이 2지문」.
3. **합성 계정 본인 판정 불일치** — v4 직접 확인은 합성을 뺐고 기존 지도는 같은 기준이었다 → 본인 판정 통일(DECISIONS 2026-10-11). 집단 통계는 그대로 합성 제외.
4. **적용 단계 콘텐츠 0** — 개발 DB 의 활성 「주장과 근거」 과제 9개가 모두 20번(확인 묶음 자체)이었다.

### 4-1. 출시 승인 뒤 실측(2026-10-11)

사용자 「승인」으로 2026#23 · M2609#23 을 활성화(검증 계획 planned 연결 · 승인자 · 사유 기록)하고 E2E 를 다시 돌리자, **2026#23 이 「다른 글에 적용」이 아니라 확인 문항으로 끌려 들어갔다** — 지도 확인 라인 a4-4(선지 맞대기)의 대상 목록에 2026#23 이 원래 있었고, 문항 과제가 살아나자 확인 묶음(9 → 10)에 붙었다. 승인 범위 밖 노출이라 2026#23 적용을 중단(paused · 사유 기록 · 삭제 아님)했다.
근본 수정: 확인 묶음을 만들 때 대상 조건 `role: "transfer"` 인 적용은 확인 문항에서 뺀다(`product-server.loadMapPracticeLinks` · `isTransferRole` · 테스트). 전이 적용 행은 모두 role=transfer.
추가 후보 4(지도 확인 라인 대상 밖) 맹검 판정 → 채택 2: 2020#24(주장 2 · 관계 4=reason) · 2021#24(주장 0 · 관계 3=example). 보류 2: M2606#24(원문 스캔 오류 조각) · M2609#24(앵커 불일치). 적용 초안 2 + 검증 계획 — 출시 승인 대기.
