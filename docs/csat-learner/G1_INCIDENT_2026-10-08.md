# G1 incident: read-only test leakage cleanup (2026-10-08)

| 항목 | 내용 |
|---|---|
| 분류 | DB 읽기 전용 계약 위반 1건 · 영향은 분석 이벤트 3행 · 학습 데이터 영향 없음 |
| 상태 | **정리 완료** (사용자 삭제 승인 · 같은 날) |
| 작업 단위 | 기출 학습 vNext G1 (`feat/csat-learning-loop-g1`) |

## 무엇이 일어났나
G1은 「DB 쓰기 일체 금지(SELECT만)」로 승인되었습니다. E2E(`csat-learning-loop.spec.ts`)는 학습자 화면의 모든 쓰기 요청을 가로챘습니다. 그러나 **`beforeAll` 로그인 단계의 브라우저 컨텍스트에는 가로채기가 없었습니다.** 그래서 로그인 뒤 첫 화면(`/hub`)이 보낸 `screen_viewed` 이벤트가 실제 `funnel_events`에 들어갔습니다(실행 3회 × 1행).

## 식별 근거 (삭제 전 SELECT)
- 테이블에는 브라우저·세션 식별 열이 없습니다. 그래서 아래 다섯 조건이 **모두** 맞는 행으로 한정했습니다.
  - 계정: 검증 계정 `runtime-test-0705@vocaflow.dev` (user_id `c02f0968-…46d1`)
  - 시각: G1 잠금 시작(04:08:24 UTC) 이후, 04:34:13–04:38:02 UTC. E2E 세 번의 시작 시각과 일치
  - 이벤트: `screen_viewed`, `surface=other`
  - 화면: `meta.screen = 'hub'` (로그인 직후 착지 화면)
  - PK: **25756 · 25766 · 25767**
- 같은 조건의 행은 정확히 3행이었고, G1 시작 이후 그 계정의 다른 행은 0행이었습니다.

## 정리 (한 트랜잭션)
- PK 세 개와 위 조건을 모두 `WHERE`에 넣은 `DO` 블록으로 실행했습니다.
- 삭제 전 3행이 아니거나, 삭제한 수가 3이 아니거나, 삭제 뒤 0행이 아니면 예외를 던져 **전체를 롤백**하도록 했습니다. 예외 없이 커밋되었습니다.
- 삭제 뒤 확인 결과:

  | 확인 | 결과 |
  |---|---|
  | 대상 PK 3개 | 0행 |
  | 검증 계정의 오늘 행 | 17 → **14** (정확히 −3) |
  | G1 시작 이후 그 계정의 행 | 0 |

- 다른 계정이나 실제 사용자 행에는 조건상 닿지 않습니다(PK와 user_id를 함께 지정했기 때문).

## 원인과 재발 방지
- **원인**: read-only E2E에서 로그인 단계의 analytics write interception이 누락되었습니다.
- **재발 방지**: `beforeAll` 컨텍스트에도 `/api/analytics/event` 가로채기를 넣었습니다(`36af66acc`). 다시 실행해 확인했습니다.
  - E2E 11/11 통과
  - 개발 서버 로그에 분석 이벤트 요청 0건
  - DB에서 G1 시작 이후 해당 계정의 새 행 0건
- **규칙**: DB 무쓰기로 검증할 때는 **로그인을 포함한 모든 브라우저 컨텍스트**에 쓰기 가로채기를 둡니다. 로그인 컨텍스트도 화면을 그리고 이벤트를 보냅니다.
