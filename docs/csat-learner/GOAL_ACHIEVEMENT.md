## 저장과 기간 배분

- 기존 `csat_map_goal_version`의 시험·점수·선택 등급·목표일·id를 사용한다. 등급만인 목표는 기존 DB의 점수 필수 제약 때문에 지원하지 않으며 임의 점수로 채우지 않는다.
- 상단 요약도 점수에서 목표/기록 등급을 만들지 않는다. 저장한1~9등급만 사용하며, 적격성 검사를 거치지 않은 최근 기록으로 ‘목표까지 N점’을 표시하지 않는다. 목표 대비 판정은 아래 단일 독립 평가 계약을 따른다.
- `20261023090000_csat_goal_budget.sql`은 **개발 DB 미적용·사용자 승인 대기**다. nullable `planning_budget` 열과 검증 함수·service-role 전용 `csat_map_goal_budget_set`을 추가한다. 새 예산은 새 목표 버전에만 저장하고 옛 목표·PLAN을 수정하지 않는다.
- 예산은 주간0~10080분·월~일7칸0~1440분/합계≤주간 또는 null·잠정 단위1~240분·우선 TASK다. API가 보류/알 수 없는 우선 TASK를 거절하며 SQL은 형식·유일성·최대21개를 검사한다. 0은 배정 없음, null은 미지정이다.
- 목표 버전의 명시 예산이 우선이다. 기존 `csat_dx_profile_hist.weekly_hours`는 분으로 변환한 입력 제안만 제공하며 저장/배정된 예산으로 승격하지 않는다. 기간 계획에는 시험·목표일·점수·저장 주간 예산이 필요하다.
- 예산 저장에는 화면에서 본 `expectedGoalVersion`이 필요하다(첫 목표는null). 설치 후 예산 해제(SQL NULL)를 포함한 목표 저장은 새 writer의 동일 사용자 잠금 안에서 최신 id를 비교한다. 다른 기기에서 목표가 바뀌면409 `goal_changed`다. 성공한 같은 키 재전송은 원래 영수증을 반환한다. 본문 일치는 서버의 불변 저장 행 대조가 책임지며 SQL 단독으로는 키만 비교한다.
- 열 미설치만 기존 조회로 전환하며 권한/연결 오류는 숨기지 않는다. RPC 미설치 시 기존 무예산 목표만 옛 writer로 저장한다. 기존 예산 보유·새 예산 저장은503 `budget_not_installed`이고 저장 성공으로 표시하지 않는다.
- 시간은 사용자가 조정하는 배분이다. 기본 단위10분은 측정 시간/교육 효과 추정치가 아니다. 요일 미지정이면 주간 한도 안에서 온전한 단위를 나누고 지정하면 요일 상한만 사용한다. 주중 진입은 남은 요일만 쓰며 지난 예산을 옮기지 않는다. 목표일 포함·과거 목표일·10년 초과·날짜 오류를 구별한다.
- 새로고침으로 오늘 예산이 되살아나지 않게 G2 수행/재시도마다 잠정 단위 시간을 차감한다. 서버 수신 시각(없으면 수행 시각)의 서울 날짜를 쓰고 중복 시도 id·합성·미래 기록을 제외한다. 도움받은 연습도 시간은 차감하지만 독립 근거는 아니다. 실제 경과 시간 계측과 구별한다.
- `goalSchedule`은 기존 NeedRank·선택 우선 TASK를 읽는다. 같은 목표/현재 단계의 유효 PLAN이 확정되고 실행 링크가 있는 수량만 편성한다. `outgoingCtx`·`withMapReturn`으로 동일 TASK/Workspace/PLAN에 복귀한다.
- 자료/도구 부족·관련성 미확인·조회 실패·PLAN 재확정·유지 기준 미정·시간 부족을 미배정 사유로 구분한다. null을0으로 바꾸거나 실행 링크를 만들지 않는다. 서로 다른 문항/지문 단위를 합산하지 않는다.
- 일정은 **현재 단계의 배분 제안**이다. 이후 단계 총량/전체 목표 달성 시점은 미확인이다. PLAN 수량·단계·근거를 바꾸거나 자동 확정하지 않는다. 과거 기준 지도에서는 현재 일정을 숨긴다.

## 계획·수행·평가·재계획의 단일 계약

`v62/goal-learning.ts`의 `goalLearning` 한 결과가 현재 목표/버전·저장 PLAN·현재 TASK 근거·학습 가능 시간·오늘/주간 제안·독립 평가·수정 이유·다음 점검 제안을 공급한다. `UnifiedLearningMap`에서 한 번 계산하며 `GoalSchedule`과 `GoalOutcome`은 결과만 표시한다. PLAN/목표 조회 오류에서 저장 상태를 만들어내지 않는다.

Claude 후속 `9f23f9b9b`의 네 상태(`no_record`·`not_judgeable`·`below`·`met`)와 `replanProposal`/`ReplanPanel`도 이 결과에 통합했다. 저장 PLAN의 목표 이력을 찾아 그 예산과 현재 예산을 각각 적용하고, 같은 오늘 날짜에서 제안끼리 비교한다. 이전 목표가 확인되지 않거나 여러 버전이 섞이면 이전 일정을 만들지 않는다. 이전 단계에는 현재 단계의 실행 링크를 빌려주지 않고 비교 전용 일정으로만 계산한다. 수정안도 PLAN 확정 전 실행하지 않는다. 새 시험 변경 사유는 응시일 문자열이 아니라 입력 시각과 저장 PLAN 시각을 비교한다. 이유 판정은 기존 `replanOf`·`planDrift` 결과 한 번만 사용한다.

다른 단계의 이전 수량은 저장 계획량 기준의 투영이며 그 단계의 현재 잔량이 아니다. 같은 단계일 때만 현재 수행량을 차감한다. 두 경우 모두 과거 달력 이력을 복원한 결과로 표현하지 않는다.

| 책임 | 정본 |
|---|---|
| 독립 근거·Need·현재 단계/수량·실행 링크 | 기존 G2·v4 PLAN/Workspace 계산 |
| 이전 PLAN 대비 단계/요구 변경과 이유 | 보존 브랜치의 `replanOf`를 `v4/replan.ts`로 추출, 기존 `planDrift` 재사용 |
| 예산·일정 | `goalSchedule`·`budgetUsage`; 기존 `scheduleChanges`는 브라우저 이전 제안과 임시 비교 |
| 시험 관찰·등급·최종 목표 판정 | `goalOutcome` |
| 확정/이력 | 기존 목표 writer·PLAN API; 제안이 저장 이력을 덮지 않음 |

수행 결과가 바뀌면 기존 독립 판정에서 다음 TASK 단계와 제안을 다시 만들고, 변경된 PLAN은 Workspace에서 재확정한다. `check_result`·`goal_change`·`content_change`·`definition_change`·`new_exam`을 구별한다. 새 시험 점수만으로 개별 TASK를 해소하지 않는다. 서버 갱신 시 주간 제안을 현재 근거/잔여 예산으로 다시 계산한다. 별도 주간 writer를 만들지 않는다. 저장 PLAN에 주간 수행 기준값이 없어 누적 수행을 ‘이번 주 수행’으로 이름 바꾸지 않는다.

목표일로부터 내부 역산은 허용한다. 화면에는 목표일·주간 계획·다음 점검 제안일을 표시하고 `목표일까지 N일 남음` 등의 카운트다운은 표시하지 않는다. `/plan`의 일반 자료×활동 계약은 유지한다.

## 목표 대비 관찰과 최종 달성

- 주입한 `asOf`까지 입력된 본인 기록만 사용하며 미래 응시일/수신 시각을 제외한다. 목표 생성 시각의 서울 날짜 **뒤** 기록만 후속 평가다. 같은 날은 응시 시각이 없어 선후 미확인이다.
- 목표 종류의 최신 기록을 고르며 나중에 입력한 다른 종류가 가리지 않는다. 분석 적격·입력 신뢰·live 응시·앱 내 문항/공유 지문 미노출을 모두 확인해야 점수 기준을 관찰한다. retake·앱 연습·진단·이전 같은 시험지는 제외하고 모드/노출/조회 실패는 미확인이다.
- 기존 노출 reader의 G2 시도·세션(삭제 포함), 함정·문제지·복습 큐·DX 응답/응시를 재사용한다. 해당 DX 기록 자체는 제외하고 응시일 이전 노출을 검사한다. 같은 날·시각 불명·큐 최초 생성시각 부재는 관련 문항/지문에서 미확인이다. 잘린 원장은 미노출로 승격하지 않는다. 앱 밖 사전 노출은 증명할 수 없다.
- 같은 종류여도 다른 시험지는 동등 난도로 간주하지 않고 점수 변화량을 계산하지 않는다. 같은 시험지 전후 점수는 **재풀이 관찰**로만 보여 주며 독립 평가/교육 효과가 아니다. 이 경로는 첫 풀이 적격성 경로와 분리한다.
- 유효 원점수0~100만 목표 점수 기준과 비교한다. 저장된1~9등급만 비교하고 점수에서 만들지 않는다. 점수 충족·등급 미충족이면 유지 단계로 보내지 않는다.
- 단일 시험은 ‘이 시험 기록은 설정한 목표 점수 기준을 충족했어요’로 표시한다. `goalOutcome.attainment` 는 계속 `unconfirmed` 이고, 최종 달성은 아래 **최종 평가 결속**으로만 판정한다. 목표 종류/날짜만으로 최종 평가를 임의 지정하지 않는다.
- TASK 해소 수·계획 수행량은 별도 활동 사실이다. 목표 달성률·교육 효과·확률·퍼센트로 변환하지 않는다.

## DB 승인

기존 데이터 수정/삭제/대량 적재·새 테이블은 없고 기존 목표/PLAN writer·추가 전용 트리거·RLS는 유지한다. 새 writer는 service_role만 실행한다. 복구 시 앱을 옛 writer로 복귀하고 새 열/이력을 보존한다. 삭제 롤백은 실행하지 않는다. 공유 DB 적용 전후 checkpoint·스키마/권한/읽기 검증이 필요하다.

원문 SHA·독립 검증 사례·수용 기준·미실행 게이트는 [독립 수용·SQL 승인 패키지](./GOAL_ACHIEVEMENT_ACCEPTANCE.md)를 따른다.

## 재처방 — 저장 계획 → 수정안 비교(`v62/replan.ts` · `ReplanPanel`)

- 새 독립 수행·시험 기록으로 `goalPlanRows.planGate='replan'` 이 된 TASK만 대상이다. 저장 PLAN 의 단계·계획량 그대로의 일정과 지금 단계·남은 양을 확정했다고 본 일정을 같은 `goalSchedule`(같은 예산·사용량)로 투영하고 기존 `scheduleChanges` 로 비교한다(재구현 없음).
- 보이는 것: TASK 단계 변화(저장 → 지금), 이번 주 배정 분 변화, 목표일까지 배정 수량 변화, 다음 주 우선 TASK, 다음 확인 배정일, 재계획 사유(`goal_change`·`check_result`·`new_exam`·`content_change`). 단계·수량·일정이 같으면 「바뀐 것 없음」.
- 저장하지 않는다. 「수정안 확인하고 확정하기」는 Workspace 계획 탭(기존 명시적 확정·버전 보존)으로만 간다. 재확정 전에는 오늘의 학습 실행 링크를 열지 않는다(기존 관문). 저장 계획 조회 실패면 패널을 만들지 않는다.
- 수정안의 실행 링크는 지금 PLAN 의 실제 다음 활동뿐이고, 없으면 만들지 않는다(그 TASK 는 미배정 사유로 남는다).
- 검증: `replan.test.ts`, `goal-outcome.test.ts`, 격리 브라우저 `pnpm --filter web exec tsx scripts/build-goal-outcome-harness.mts` → `playwright test -c playwright.isolated.config.ts goal-outcome.browser.spec.ts`(1440/1280 · 기록 없음·미달+재처방·충족·재풀이·다른 시험·목표 변경·조회 실패). 합성 상태이며 공유 DB 종단이 아니다.
- UI 정책: 「오늘의 학습」은 목표일만 표시하고 「N일 남음」 카운트다운은 없앴다(LEARNER_MANAGEMENT §2-2 예외 조항과 일치).

## 직접 확인 판정의 코드북 조건(T-0096 · `skill-diagnosis.ts`)

- 정책은 TASK 코드북 문장에서 도출한다(`reachPolicyOf`) — 정본을 바꾸지 않는다. 지금 정책이 판정에 실제로 쓰이는 TASK: E2(다른 날), R1(서로 다른 지문), R5(둘 다), E3·R2(관찰 제한). V1 은 문장상 「다른 날」이지만 확인 키가 없어 이 판정을 타지 않으며, DEC-01 의 낱말별 재인출 계약은 구현하지 않았다.
- **관찰 제한(E3 「함정 선택만으로 약함 판정 금지」 · R2 「관찰 근거 내역만」)**: 객관식 정오만으로 학습 요구(verified·still_needed)를 확정하지 않는다. 채점 `isCorrect` 는 그대로 두고 진단 자격에서만 막으며, 저장된 과거 정오 기록도 조회 때 다시 판정된다. 독립 시도 수 관찰은 남는다.
- **서로 다른 지문**: 다시 확인 연속 정답은 서로 다른 지문(확인 링크의 DB 지문 정체 `passageKey`)이어야 한다. 지문 정체를 모르면 초기 확인 연속과 지연 재확인 모두에서 세지 않는다(문항을 지문으로 대신 세지 않음). 서로 다른 지문 조건이 없는 TASK 는 지문 키와 무관하게 서로 다른 문항으로 센다.
- **다른 날(D4-DEC-01)**: 연속 정답으로 초기 확인을 마친 시각 t0 뒤의 **별도** 재확인 정답이 t0 와 다른 KST 날짜 · 12시간 이상일 때만 `resolved`. 그 전은 `pending_delayed`(As-Is `checking` · 처방 닫힘 · 다음은 다른 날 확인). 12시간은 Pilot 운영 하한이다. `resolved` 를 도달로 자동 변환하지 않는다.
- 확인 키별 판정 분리는 유지한다(R5 창작/기출 키의 오답을 합쳐 확정하지 않음). 채점 범위 통일은 별도 측정 계약.
- 분리(이번 범위 밖): D4-DEC-02 선택형 proxy 별도 합계 · DEC-03 R3/R4 잠정 공통 1묶음 · DEC-04 S1 서로 다른 문장 3연속 — PLAN 집계 계약이라 별도 TASK.

## 화면 구조(T-0110 · learning_interaction)

- 「목표 대비 지금」: 0~100 점수 축에 목표 표식과 이 기록 표식을 함께 두고(같은 종류 시험 원점수가 있을 때만 · 퍼센트·예측 없음), 「시험 기록이 말하는 것 | TASK 활동이 말하는 것」 대조 2열로 보인다. 점수 충족 · 기록 등급 없음이면 판정 불가 그대로이고 다음 안내는 `record_grade`(등급 기록 확인)다.
- 「계획 다시 세우기」: TASK 행 × (단계 저장→지금 · 지금 배정 · 저장 계획대로 · 수정안) 비교표. 합계는 표의 행과 같은 TASK 집합(「수정안 대상 소계」)이고, 이번 주 전체(다른 TASK 포함)는 값이 다를 때만 별도 행으로 구분한다. 「지금 배정」은 실제 일정(`goalSchedule` 입력 그대로 — 재확정 전 TASK 는 0)이라 오늘의 학습과 같은 값이다. 확정 버튼은 카드 안쪽 여백 안.

## 최종 평가 결속(`v62/final-assessment.ts` · `FinalAssessment`)

- **대상**: 학습자가 목표 버전마다 한 번 명시한 「목표 시험 종류(`target_exam`) · 응시일」. 추론하지 않는다. 목표 버전이 바뀌면 결속은 이어지지 않는다(새로 정한다). 옛 결속은 지우지 않는다.
- **시점**: 응시일은 목표를 정한 서울 날짜의 **다음 날 ~ 목표일**. 응시일 전 `scheduled`, 지난 뒤 그날 목표 종류 기록이 없으면 `awaiting_record` — 다른 날 · 다른 종류 · 나중 기록으로 대신하지 않는다.
- **자격 · 비교 가능성**: 응시일까지의 기록에 `goalOutcome` 을 그대로 적용한다(첫 풀이 · live · 분석 적격 · 입력 신뢰 · 앱 노출 없음 · 같은 시험지 재풀이 아님 · 유효 원점수). 노출 원장은 결속 기록에 대해서도 따로 읽는다(`load.ts`). 하나라도 확인 못 하면 `not_judgeable`(사유 보존).
