# Factory I1 — 사용자 결정 · 승인 대기

> 각 항목은 「지금 상태 · 권고 · 결정하지 않으면」을 적는다. **DB 변경 승인은 항목 1 하나로 시작한다** — 나머지는 그 뒤 또는 독립.
> 패키지: [FACTORY_I1_APPROVAL_PACKAGE.md](./FACTORY_I1_APPROVAL_PACKAGE.md) · 감사: [FACTORY_I1_SECURITY_AUDIT.md](./FACTORY_I1_SECURITY_AUDIT.md)

## 1. DB 변경 승인(사용자만)

| # | 승인 요청 | 권고 | 승인하지 않으면 |
|---|---|---|---|
| **DB-1** | C → B → I1-S 를 개발 DB 에 한 트랜잭션으로 적용(sha256 은 패키지 §2) | 승인 권고 — 공급 경로가 열리기 전에 D1/D2 가 함께 들어가야 한다 | 영속 수요 · 주문 · 공급 0 그대로. 앱은 `not_installed` 로 정직하게 보인다 |
| DB-2 | I1-P 적용 | P-1 · P-2 확인 뒤 승인 | 부분 납품이 기록상 「공급 완료」로 닫힐 수 있다(I1-S 의 수량 상한은 그대로 동작) |
| DB-3 | I1-D3 적용 | **보류 권고**(D3-1 · D3-2 미정) | 공용 생산 계보 없음 — 학습자별 주문은 `production_run_id` 문자열만 |

## 2. 정책 결정

| # | 질문 | 지금(이 PR 구현) | 대안 |
|---|---|---|---|
| P-1 | `delivered` 의 뜻 | **전이 시점에 유효한 해당 주문 공급 전량**. 일부면 `partial`(공백 아닌 이유 필수). 이후 철회로 주문 이력을 고치지 않는다 | 역사적 행 수만 세면 철회된 자료로도 종결된다(독립 R02 반증) |
| P-2 | 남은 부족을 무엇으로 세나 | 줄 수량 − **지금 유효한** 공급(승인 철회 · 산출물 변경이면 다시 부족) | 주문 기준 — 권리 철회 뒤 부족이 안 보인다 |
| P-3 | PLAN 이 바뀌면 옛 줄의 열린 주문 | 자동 취소 없음. 관리자가 held/failed 로 닫는다. 새 PLAN = 새 수요 · 새 줄 | 자동 failed(이유 plan_revision) — 생산 중인 것이 버려질 수 있다 |
| P-4 | 자격이 대체(supersede)되면 이미 공급된 행은 | **이력 보존, 현재 유효 공급 제외**. 새 자격·승인은 옛 공급에 자동 상속하지 않는다(독립 R01). 공급과 supersede 잠금 직렬화 | 근거 보강도 현재성 재검수가 필요하다. 같은 줄·산출물 unique 유지: 다른 적격 산출물이나 새 수요 필요. 옛 원장 삭제 금지 |
| P-5 | 「문항 화면만 연 것」(`item_seen`)을 평가 공급 거절 사유로 | 거절(문제를 읽었으므로 첫 독립 시도가 아니다) | 허용 — 공급 가능 문항이 늘지만 첫 시도 독립성이 약해진다 |
| P-6 | 합성(synthetic) 원장 행도 노출로 | 센다(보수적) | 뺀다 — 실제 학습자 원장에 섞인 시험 행이면 공급이 막힐 수 있다 |

## 3. 화면(이 PR 에서 구현 · PC 검증함)

| # | 변경 | 근거 | 확인 |
|---|---|---|---|
| UI-1 | 교수 역할(원문 분석 · 모델 설명) 줄: `available`(「지금 학습할 수 있어요」) → `readable_unreviewed`(「지금 읽을 수 있어요 · 수업용 검수 전」). 해설 열람은 그대로 | SQL `fq_role_ok` 는 교수 적합성(D) pass 를 요구하는데 화면은 검수 전 해설을 「쓸 수 있음」 · `fully_supplied` 로 셌다 | PC 1440 REPAIR 단계 실제 문구 확인(⑥) |
| UI-2 | 공급 단계 `delivered` 는 요청 수량 · 유효 공급을 서버가 계산했을 때만. 일부면 「일부 공급됨 · 남은 자료 준비 중」, 모르면 「공급 기록 있음 · 수량 확인 전」 | 공급 행 하나로 「공급 완료」를 쓰던 것 | 단위 시험. 실제 화면은 DB-1 · DB-2 적용 뒤에만 나타난다(지금은 기록 표 없음) |

여섯 공급 구분(지시 §6)의 대응: ① 지금 열람 가능한 기존 해설 = `readable_unreviewed`/`read_now` ② 교수 검수 전 자료 = 같은 줄의 `teaching: null`(공급으로 세지 않음) · 공장 재고는 `factory_candidate` ③ 정식 적격 공급 = `available`(자격 확인) · 실제 공급 행 `delivered` ④ 공급 승인 대기 = `awaiting_release` ⑤ 원장 미설치 = 기록 `not_installed` ⑥ 조회 실패 = 기록 `error`(「없음」으로 삼키지 않는다). 정상 0건 = `installed` 이고 줄 기록 없음.

## 4. D3 — 공용 생산 계보(별도 승인)

| # | 미정 | 왜 필요한가 |
|---|---|---|
| D3-1 | Product Order 를 누가 발행 · 등록하나(공장 드레인 · 관리자 콘솔 · 에이전트) | 등록부는 「공장이 실제로 발행한 주문」만 담아야 현재성 검사가 의미 있다 |
| D3-2 | `order_hash` 의 정본 계산(공장 `order-production-run.ts` 의 어느 직렬화) | 앱 · DB · 공장이 같은 해시를 내야 링크 검사가 성립한다 |
| D3-3 | 공용 생산 1건이 여러 학습자에게 **어떤 순서 · 수량으로** 배분되나 | 지금은 링크만 — 배분은 학습자별 공급(D2 재검증)이 한다. 공정 배분 규칙은 없다 |

독립 검증: **DB-3 보류 유지**. SQL은 제출 hash의 형식·현재 revision·TASK·role만 검사한다. 정본 hash를 계산하지 않으며 `share_key`와 개인 주문 요구 비교, 링크/공유 배분량의 `quantity` 제한도 없다. 기존 링크 재전송은 과거 사실 반환이며 현재 revision 승인으로 해석하지 않는다.
