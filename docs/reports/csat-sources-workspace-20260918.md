# 원문 관리 작업 공간 재설계 · 2026-09-18

## 조사와 실제 업무

`/admin/csat/sources`는 평가원 PDF 보관함이 아니라 교재용 기사·도서 발췌의 **원천별 재고와 적격 스캔**이다.
`page.tsx`는 관리자 가드 뒤에서 JSON 스냅샷 두 개를 읽으며 DB를 수정하지 않는다.
직접 DB 조회로 `library_articles`, `csat_dcp_items`, `csat_source_snapshots` 존재와 원천 21종을 확인했다.
라이브 조회와 재고 스냅샷의 수가 다르므로 새 UI도 실시간 집계라고 표현하지 않는다.

실제 흐름:

`소스별 수집기 → library_articles → ACP 큐 분석/검수 → 내용 판정 드레인·필요한 발췌 → 적격 7축 스캔 → 교재 조판`

- 내부 수집 상태(`queued`, `ready`, `published`, `failed`, `archived` 등)와 적격 6등급은 다른 축이다.
- `ready`는 ACP 검토 대기다. `usable`·`excerpt`만 조판 가능하며 source 전체가 적격이라는 뜻이 아니다.
- 법적·게재 안전·게시 게이트·학령 분석·내용 판정·지문 규격·어휘가 실제 적격 7축이다.
- PDF parsing·문장 anchor·평가원 정답 존재를 이 페이지의 적격 기준에 새로 넣지 않는다.
- 원문 열람·수정·보관·삭제, 지원되는 일괄 처리는 기존 `/admin/articles`와 `preview/[id]`가 소유한다.
- 소스 검색·필터·정렬은 없었고 21행이 긴 기준표 뒤에 있었다. 실브라우저에서 목록이 첫 화면 밖임을 확인했다.
- 기존 12개 절과 명령을 보존하되, 지금 처리할 원천을 찾는 일과 규격·생산 진단을 분리한다.

관리자 질문의 우선순위는 **어느 원천을 확인해야 하나 → 무엇이 빠졌나 → 어떤 원문을 열어 고치나 →
언제 잰 결과인가 → 전체 조판 적격은 왜 이 값인가**다. 원천별 적격 통과 수는 현재 스냅샷에 없으므로 만들지 않는다.

## IA 결정 (구현 전)

| 안 | 실제 업무에 대입 | 결정 |
|---|---|---|
| A · 통합 작업 공간 | 21개 원천을 검색·문제별 필터로 좁히고 같은 화면에서 상태·조치를 확인 | 채택 |
| B · 목록 + 별도 상세 route | 원천별로 이동이 늘고, 원문 수정 상세는 이미 ACP에 존재 | 새 route를 만들지 않음 |
| C · 운영 상태별 route | 문제 조건이 겹치므로 같은 원천이 여러 페이지에 반복되고 복귀 맥락을 잃음 | 문제 필터로 흡수 |

화면은 **기존 route 하나**. `원천 관리`는 목록과 선택한 원천의 판단 패널,
`적격 판정`은 7축·등급·학령과 추출 결함, `처리 안내`는 드레인·유형 재고·생산 진단을 맡는다.
검색·문제·정렬·선택·보기는 URL에 남겨 새로고침과 뒤로 가기에서 복구한다.
21개 집계행에는 페이지 나누기가 필요하지 않다. 원문 수십만 행은 기존 ACP 서버 페이지 처리를 재사용한다.

유지: 관리자 가드, 판정 정본·스캐너·스냅샷, 기존 상세 표, NextStepPipeline, AdminScreenHelp, ACP 액션.
수정: SourceEligibilityClient의 정보 배치, SourceInventoryTable의 목록·상세, source-inventory-view의 잘못된 명령 처방.
신규: 작업 공간 상태·문제 필터 모델, SourceWorkspace, CSS 모듈과 동작 회귀.
삭제 후보: 중복 KPI 카드, 원천 요약 띠, 현재 원천에 적용되는 것처럼 보이는 전역 배치 명령.

잘못된 조치의 확인: 기존 행 처방은 다른 원천에서도 `--feed plos-extract`를 제안하고,
게이트 export의 원천 제외 조건을 무시했다. 원천 패널의 주 행동은 범위가 명확한 ACP 검수 링크로 바꾼다.
전역·DB 쓰기 명령은 처리 안내에 전제와 함께 남기고, 원천별 원클릭 처리나 새 일괄 API를 만들지 않는다.

## 렌더 비평과 수정

검토 환경: `/admin/csat/sources`, Chromium, 2026-09-18 KST. 데스크톱 1280/1440/1920×900,
좁은 화면 390×844. 기본 목록·원천 선택·검색 결과 없음·판정/처리 보기·펼친 상세 표를 확인했다.
라이트 목록/상세와 다크 모바일 상세를 실제 PNG로 열어 읽었고 키보드 조작은 브라우저에서 검증했다.

| 관찰 위치 | 관리자에게 생기는 문제 | 수정 및 코드 위치 | 재검증 |
|---|---|---|---|
| 첫 화면의 KPI·공정·긴 판정 기준 | 원천을 찾기 전에 보고서를 읽게 됨 | `SourceWorkspace`의 기본 목록과 판정/처리 탭으로 분리. 첫 구현 뒤 `sources.module.css` 상단 간격도 축소 | 3개 데스크톱에서 첫 행 하단 763→723px. 기존 화면에서는 목록이 화면 밖 |
| 필터 select의 label | 옵션 전체가 접근성 이름에 포함되어 정확한 이름으로 조작할 수 없음 | 별도 `label htmlFor`와 select ID 연결 | 검색·문제 필터·정렬 E2E 통과 |
| 모바일에서 펼친 상세 표 | grid의 최소 콘텐츠 폭이 페이지 전체를 836/776px로 늘림 | 상세 grid에 `minmax(0,1fr)`, 자식 `min-width:0`, 명령 줄바꿈. 표 내부 가로 스크롤은 유지 | 두 보기의 접힌 절을 모두 펼쳐도 문서 가로 넘침 0 |

원천 검토 버튼은 선택·확장 상태를 전달하고 상세 제목으로 포커스를 보낸다.
닫으면 검토 버튼으로 복원한다. 필터 때문에 버튼이 사라진 경우 원천 관리 탭으로 복원한다.
탭은 좌우 방향키·Home/End로 움직이며, 보기 변경 버튼도 해당 탭으로 포커스를 옮긴다.
색은 법적 제약/실패의 유일한 전달 수단이 아니며 문구·편수·아이콘을 함께 사용한다.

## 범위와 남은 한계

DB 조회는 현황과 테이블 존재를 검증하는 읽기만 수행했다. 마이그레이션·DB 적재·발행은 실행하지 않았다.
화면은 기존 스냅샷을 계속 사용하며 실시간 동기화나 원천별 적격 통과 수를 새로 제공하지 않는다.
원문 편집/삭제의 종단간 실행은 이번 UI 검증에 포함하지 않았다. 기존 ACP의 원천/상태 query 연결을 검사했다.
프로덕션 전체 빌드·다른 브라우저·전체 저장소 테스트는 이번 검증 범위에 포함하지 않았다.
