# Production evidence resolver: code validation status

`scripts/textbook/production-evidence-resolver.mjs` calls the existing DB-backed `verifyOrderRenderItems` for every section in a single-grade or multi-grade order. This checks the current child and source body, rights, ready status, product order revision, promotion audit, current authority, certificate/eligibility revocation, signed Gold-S/seed request and printed item/explanation digest. For multi-grade groups it additionally checks each child order, source/rights hash, passage hash, benchmark snapshot and item-set hash against the sealed group evidence. A second read pass rejects changes observed between section checks. A failure in any grade rejects the whole volume.

The single-grade `render-volume.mjs --product-order` path now uses this resolver and writes the evidence snapshot into its lineage sidecar. `runLiveMultiGradeFactoryDryRun` derives current lineages from the resolver, then passes them to the multi-grade unit/HTML runner; it does not trust lineages supplied alongside stage artifacts. Synthetic DB fixtures exercise two grade sections and fail injection for changed item/explanation, revoked certificate, queued child, blocked child/source rights, wrong order revision, expired authority, mixed group evidence, and source mutation between read passes.

The returned snapshot is `live_revalidated_non_atomic`, `production_verified=false`. These Supabase REST reads do not share a transaction, so a change after the final read cannot be excluded. The multi-grade group analysis, activity and unit evidence are still caller supplied, although internally hash checked. There is no real benchmark corpus, real Gold-S, production publication, or DB seed in this work. A transactional DB-side final check and an actual admitted candidate remain required for operational production verification.
