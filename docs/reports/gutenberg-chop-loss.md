# 구텐베르크 발췌가 버리던 것 — 본문의 54.9%

**측정 2026-09-24 · 12권 1,312,273어를 원문째 받아 사유별로 가름(잔여 0어, 100% 설명됨)**

> 질문은 하나였다. **"왜 이 소스는 발췌를 했나? 특정 사이즈로 발췌하면 다양한 유형의
> 교재 생성이 어렵지 않나? 발췌 기준이 뭔가?"** — 옳은 질문이었고, 재 보니 더 나빴다.

---

## 1. 무엇이 DB 에 있나

`library_articles` 에서 `source='gutenberg'` 인 **40,519행은 책이 아니다.** 평균 263어,
범위 94~415어의 **발췌 조각**이고, **1,810권**에서 나왔다(권당 22.4조각).

| | |
|---|---:|
| 책 | 1,810권 |
| 조각 | 40,519 |
| 권당 조각 | 22.4 |
| 권당 남긴 낱말(중앙) | **2,080어** |
| 한 행의 최대 길이 | 3,092자 |

**원문 전문은 DB 어디에도 없다.** 가장 긴 행이 3KB 다. 같은 책에서 더 뽑으려면
Gutenberg 에서 다시 받아야 한다(`source_url` 과 `source_id` 에 책 번호가 있으므로 가능하다).

두 번에 걸쳐 수확됐고 창이 서로 달랐다:

## 2. 발췌 기준 — `chop()` 한 함수

```js
function chop(body, lo = 300, hi = 340) {
  const paras = body.split(/\n\s*\n/)…
    .filter((x) => x.length > 80 && /[.!?]/.test(x))   // ① 짧은 문단은 버린다
  let buf = [], n = 0
  for (const para of paras) {
    const w = para.split(/\s+/).length
    if (w > hi) continue                                // ② 340어 넘는 문단을 통째로 버린다
    buf.push(para); n += w
    if (n >= lo) {
      if (n <= hi + 60) out.push(buf.join(' '))         // ③ 400어를 넘기면 버퍼를 그냥 비운다
      buf = []; n = 0
    }
  }
  return out                                            // ④ 마지막 buf 는 안 내보낸다
}
```

창이 **300~400어 하나로 고정**돼 있었다. 저장소의 정본 창은 넷인데(`compose-unit.ts`)
그중 하나만 겨냥한 것이다.

### 무엇이 얼마나 사라졌나

| 사유 | 낱말 | 비율 | 어느 줄 |
|---|---:|---:|---|
| **남긴 것** | 592,357 | **45.1%** | ← DB 에 들어간 조각 |
| 340어 넘는 문단 | 279,780 | **21.3%** | ② `if (w > hi) continue` |
| 400어 넘긴 묶음 | 401,152 | **30.6%** | ③ 버퍼를 그냥 비운다 |
| 비산문(80자 이하) | 37,758 | 2.9% | ① 표·목차·시행 — **이건 버리는 게 맞다** |
| 마지막 꼬리 | 1,226 | 0.1% | ④ |
| 합계 | 1,312,273 | 100.0% | |

**앞의 둘이 문제다. 둘 다 「자를 자리를 못 찾았다」는 이유로 글을 버린다.**
340어짜리 문단은 쪼개면 되고, 창을 넘긴 묶음은 마지막 문장을 다음 묶음으로 넘기면 된다.

### 더 나쁜 것 — 무엇이 버려졌는가

340어를 넘는 긴 문단은 **1900년대 논설·철학·역사서의 전형**이다. 즉 이 저장소가 가장
아쉬워하는 **논증 밀도가 높은 산문**이 계통적으로 빠졌다. 책마다 편차가 크다:

| 책 | 340어↑ 문단이 차지한 몫 |
|---|---:|
| 54968 | 39.3% |
| 4201 | 36.2% |
| 833 | 31.1% |
| 42560 | 30.3% |
| … | |
| 44732 | 0.5% |

### chop() 밖에서 또 버려진다

chop 이 내보낸 45.1%(592,357어) 중 DB 에 남은 것은 **68,315어(5.2%)** 다.
나머지 88.5% 는 `looksLikeBookMatter` · `fitRecord` · `looksNarrative` · 소재 몫이
걸렀다. **이쪽은 품질 필터라 정상**이다 — 문제는 그 앞단에서 이미 절반이 사라져 있었다는 것.

## 3. 고친 뒤 — 같은 12권

`scripts/csat/lib-chop.mjs` 로 떼어 내고 고쳤다:

1. 긴 문단은 **문장 경계에서 쪼갠다**(버리지 않는다)
2. 창을 넘길 것 같으면 **먼저 내보내고** 그 문장을 다음 묶음의 시작으로 쓴다
3. 마지막 꼬리도 하한을 넘으면 내보낸다
4. **창을 인자로 받는다** — 하나로 고정돼 있어서 다른 유형을 낼 수 없었다
5. 버린 몫을 **사유별로 세어 돌려준다** — 조용히 버리면 다음 사람이 또 발견한다

| | 낱말 | 잔존율 | 조각 |
|---|---:|---:|---:|
| 옛 `chop()` · 장문창만 | 592,357 | 45.1% | 1,741 |
| 새 `chopToWindow` · 수능 장문 260~400 | **1,266,914** | **96.5%** | **3,983** |
| 새 `chopToWindow` · 수능 짧은 90~200 | 1,262,361 | 96.2% | 9,180 |
| 새 `chopToWindow` · 학교 문단 40~200 | 1,268,369 | 96.7% | 16,291 |

같은 창에서 **674,557어(본문의 51.4%p)** 를 되찾았다 — 조각 수로 **+129%**.
그리고 같은 본문이 이제 **창 셋을 동시에** 낸다. 옛 코드는 장문창 하나만 냈다.

회귀 9건: `scripts/csat/__tests__/lib-chop.test.mjs`(CI 의 `node --test`).
읽기 전용 실전 확인: `--feed art --books 2` 에서 조각 361 · 버린 낱말 1,353(전부 비산문·꼬리).

## 4. 그래서 이 조각들이 원문인가 — 아니다

| | gutenberg 40,519행 | 이번에 확보한 94편 |
|---|---|---|
| 단위 | **조각**(평균 263어) | **원문 전문**(정제 후 중앙 6,150어) |
| 원본 보존 | 없음 — 책의 5.2%만 | 있음 |
| 낼 수 있는 창 | 행마다 하나 | **98.9%가 둘 이상, 79%가 장문까지** |
| 이음매 | 수확 시점에 고정 | 생성 시점에 파이프라인이 고른다 |
| 순서 정보 | **없다**(`source_id` 가 본문 해시) | 원문이 통째로 있다 |

`itemWordSpec(type, band)` 이 유형마다 다른 창을 고르는 구조인데, **조각을 저장하면
그 선택이 수확 시점에 미리 박혀 버린다.** 2026-09-23 에 "원문은 길이로 판단하면 안 된다"
고 정정한 바로 그 실수가 2026-09-04 수확에 이미 들어가 있었다.

**다만 되돌릴 수 있다.** 책 번호가 남아 있고 Gutenberg 는 PD 에 번호가 불변이므로,
고친 `chopToWindow` 로 1,810권을 다시 훑으면 된다. 재수확 여부와 비용은 사용자 결정이다.

## 5. 남은 것

- **재수확 판단** — 1,810권 × 창 3개. 되찾는 몫은 위 표가 근거다. 아직 안 했다.
- **조각에 순서를 안 적는다** — `source_id` 가 본문 해시라 같은 책 조각들의 읽기 순서를
  복원할 수 없다. 조각을 이어 더 긴 지문을 만드는 길이 막혀 있다. 재수확 시 함께 고칠 것.
- **다른 수확기도 같은 자리가 있는지 안 봤다.** `harvest-plos.mjs` · `harvest-frontiers.mjs` ·
  `harvest-nist.mjs` 는 이 측정을 안 했다.
