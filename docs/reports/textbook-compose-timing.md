# 조판 173초 — 어디에 쓰이는가 (그리고 왜 지금은 안 고치는가)

**실측 2026-09-01** · `VOCAFLOW_TIMING=1` 로 재현 · 관련: 커서 페이징 수정 `a64d79b8`

## 재기 전 짐작은 틀렸다

커서로 고친 뒤에도 V6 한 권 조판이 181초였다. 커밋 메시지에 **"남은 병목은 2열 정렬을 쓰는
어휘 조회로 보인다"** 고 적었다. 재 보니 **어휘 조회는 2.6초(1.5%)** 였다.

| 단계 | 시간 | 몫 |
|---|--:|--:|
| **문항 조회 (`csat_dcp_items`)** | **150.7초** | **83.2%** |
| 사전 조회 (`shared_dictionary`) | 16.4초 | 9.1% |
| 원글 조회 (`library_articles`) | 5.7초 | 3.1% |
| 예행 조합 (CPU) | 2.9초 | 1.6% |
| 본 조합 (CPU) | 2.7초 | 1.5% |
| 어휘 조회 (2열 정렬) | 2.6초 | 1.5% |

짐작한 곳은 **56번째로 큰 몫**이었다. 그래서 `VOCAFLOW_TIMING` 손잡이를 코드에 남긴다 —
이 저장소가 A4·A6 에서도 짐작으로 원인을 짚었다가 틀린 적이 있다.

## 무엇이 150초를 쓰나

**60문항짜리 한 권을 고르려고 그 밴드 재고를 통째로 내려받는다.**

```
V6  csat_dcp_items  229,014행 × 약 2,064 B  ≈  473 MB
                    (payload 1,367 · answer_key 436 · 나머지 261)
```

## 줄일 수 있는가 — 셋 다 막혔다

**① 유형으로 서버에서 거르기 → 0바이트 절약.** 조합기가 쓰는 26종에
V6 229,014행의 **100.0%** 가 이미 들어간다(V7 도 100.0%). 지금 클라이언트에서 하는
그 필터는 아무것도 안 버린다.

**② `answer_key` 빼고 받기 → 21% 절약, 그런데 위험하다.** 선택 로직은 `answer_key` 를
읽지 않고 나르기만 한다(`compose-unit.ts` 는 타입 선언에만 쓴다). 하지만
`explain-drain-export.mjs` 가 **`pool` 에서** 그 값을 읽는다
(`rows.push(...pool.filter((p) => itemIds.has(p.id)))` → `r.answer_key?.explanation_ko`).
고른 뒤 다시 붙이는 방식은 되지만, 세 호출부의 참조 관계에 기대게 된다.
**181초 → 약 149초를 얻자고 치를 값이 아니다.**

**③ 길이로 서버에서 거르기 → 마이그레이션이 필요하다.** 길이 관문(`itemWordSpec`)은
`payload` 를 세어야 하는데 저장된 어수 컬럼이 없다. 생성 컬럼을 두면 서버에서 거를 수 있지만
스키마 변경이라 **사용자 승인 사항**이다(CLAUDE.md).

## 그래서 지금은 안 고친다

**진짜 버그는 이미 고쳤다** — OFFSET 때문에 V6·V7 이 statement timeout 으로 **아예 죽던 것**을
커서로 바꿔 살렸다(`a64d79b8`). 남은 것은 느린 것이지 죽는 것이 아니다.

조판은 상시 경로가 아니라 **가끔 도는 배치**다(`--volume all` 7권 ≈ 10분). 그 정도를 줄이려고
스키마를 바꾸거나 세 호출부의 참조에 기대는 최적화를 넣는 것은 **비용이 이득보다 크다.**

다시 아파지면 순서는 ③ → ② 다. 근거는 위 표에 있고 `VOCAFLOW_TIMING=1` 로 언제든 다시 잰다.

## 재현

```bash
VOCAFLOW_TIMING=1 npx tsx --tsconfig apps/web/tsconfig.json \
  scripts/textbook/market-benchmark.mjs --volume 6
```
