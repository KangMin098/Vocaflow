## 1. 보안 — 즉시 조치 (메인 세션 직접 재검증)

### S-1. anon 키 하나로 평가원 기출 802문항의 정답을 고치고 지울 수 있다

| 확인 항목 | 실측 |
|---|---|
| `csat_items_public` 뷰 옵션 | `security_invoker = false` → 소유자 권한 실행 |
| 소유자 | `postgres` · `rolbypassrls = true` |
| `csat_items.relforcerowsecurity` | `false` → 소유자가 RLS 우회 |
| `csat_items` 정책 | `csat_items_read :: USING (false)` — 완전히 닫힘 |
| 뷰 자동 갱신 | `is_updatable = YES` · `is_insertable_into = YES` · INSTEAD OF 트리거 0 · 규칙 0 |
| `anon` 의 INSERT / UPDATE / DELETE | **셋 다 있음** |
| `anon` 의 SELECT | **있음** |
| 노출 컬럼 | id · exam_id · no · section · in_scope · type_id · stem · **answer** · points · high_score |
| in_scope 문항 | **802** |

닫힌 RLS 위에 소유자 권한 뷰가 얹혀 있고, 유일한 관문인 그랜트가 열려 있었다.
대조군 `library_seed_catalog_view` 는 같은 조건인데 `security_invoker = true` 라 안전하다 — **차이는 그 옵션 하나다.**

`security_invoker` 를 뒤집으면 안 된다: 기반 정책이 `USING (false)` 라 CSAT 학습자 화면이 전부 0행이 된다
(`lib/csat/browse.ts:71` · `learner.ts` 6곳 · `heatmap.ts:147`). SECURITY DEFINER 자체는 의도된 저작권 경계이고
`db_health_exceptions` 에 면제도 있다 — **다만 그 면제는 SELECT 에만 유효하고 쓰기는 사유에 없다.**

→ `supabase/migrations/_pending_csat_items_public_readonly.sql` (회귀 가드 질의 포함)

### S-2. 그 밖

- **RLS 없이 anon SELECT 가 열린 테이블: 0건.** public 테이블은 전부 `relrowsecurity = true`.
- **개인 데이터 anon 노출: 없음.** `USING (true)` 14건은 전부 사전·철자·어근·빈도·방언·만화 메타다.
- **지금 성공하는 anon 쓰기: 없음**(정책이 전부 `auth.uid()=user_id` / `is_admin*()` / `TO service_role`).
  다만 그랜트가 127 관계에 열려 있어 **정책 하나만 잘못 추가되면 열리는 표면**이다.
- `anon` 이 SECURITY DEFINER 함수 **33개**를 실행할 수 있다(`enqueue_*_jobs` · `csat_source_snapshot_take` ·
  `cron_auto_promote_all_users` 등 부수효과 있는 것 포함). `funnel_summary(integer)` 는 **코드 호출처 0**인데
  퍼널 10,987건 집계를 anon 에 돌려준다.
- `pgstattuple` 확장 함수 9개가 anon+authenticated EXECUTE — 비로그인자가 임의 표의 물리 통계를 읽는다.
- **만화 표 3개가 anon·authenticated 에 `arwdDxtm` 전권**(`comic_pages`·`comic_books`·`pd_comic_issues`).
  마이그레이션이 46일 전 「REVOKE 필요(승인 대기)」로 남긴 그대로다.
- 2026-09-19 권한 마이그레이션 3편은 **기본 권한(default ACL)만** 고쳤다 — 앞으로 만들어지는 함수만 막고
  **기존 객체는 하나도 안 막혔다**. advisor 의 131·127·80·152 건이 전부 그 잔여분이다.
  TABLES/SEQUENCES 기본값은 아직 손대지 않아 **새 표마다 anon 전권이 다시 붙는다.**

## 2. 효율 — 가장 큰 낭비는 인덱스가 아니라 크론 하나였다

### E-1. `refresh_textbook_shelf_stats()` — cron 14, 30분마다

pg_stat_statements **총 7,853초 · 340회 · 평균 23,096 ms**. EXPLAIN 으로 쪼갠 내역:

| MV | 시간 | 계획 | 버퍼 |
|---|--:|---|---|
| `textbook_shelf_inventory_mv` | 10,348 ms | Parallel Seq Scan `csat_dcp_items`(880,337행) | hit 5,068 / **read 159,971** |
| `textbook_shelf_sources_mv` | 11,676 ms | Seq Scan + Hash Left Join `library_articles`(109,047) | hit 12,327 / **read 177,141** |

`read` 가 거의 전부 = 캐시 미스. 한 번 갱신에 **1.25 GB + 1.38 GB** 를 디스크에서 읽는다.
`shared_buffers` 는 **256 MB** — 한 번의 갱신이 그 10배를 읽어 **캐시를 통째로 비운다.**
30분 주기 = 하루 48회 · 약 **60 GB 디스크 읽기**. 그 사이 학습자·사전 조회가 매번 차가운 캐시에서 다시 읽는다.
CHANGELOG 에 같은 함수가 인스턴스를 굶겨 죽인 기록이 두 번 있고, 그때 고친 것은 타임아웃 상향뿐이었다.
7일 창에 `job startup timeout` 이 **14건**(373회 중 3.8%).

읽는 쪽은 관리자 화면 하나이고 드레인 import 가 끝나면 함수를 직접 부른다 — 크론은 보조망이다.
**30분 → 6시간이면 디스크 읽기 92% 감소.** → `_pending_db_efficiency_cron_autovacuum.sql`

### E-2. 가장 비싼 쿼리 — `csat_dcp_items` 키셋 페이지네이션

**총 13,897초(3.9시간) · 16,413회 · 평균 847 ms** — `WHERE type = $1 AND id > $2 ORDER BY id`.
맞는 인덱스가 없다. UNIQUE 인덱스는 `(kind, ref_id, type, paragraph_idx)` 라 `type` 이 3번째다.
EXPLAIN: 흔한 유형은 pkey 스캔+필터 263 ms, **드문 유형은 72 MB 전량 스캔 + Sort → 1,483 ms**.
호출자는 `explain-fill.mjs:132`(--overwrite) · `explain-discriminate.mjs:64`.
→ `csat_dcp_items (type, id)` 신설(35~45 MB · `CONCURRENTLY` 필요 → psql).

### E-3. `shared_word_sets` — 학습자 화면이 매번 805 ms 풀스캔

`curation_query->>'book_id'` 등호 조회인데 기존 인덱스는 `gin(jsonb_path_ops)` 라 **`->>` 등호를 원리적으로 못 받는다.**
EXPLAIN: Seq Scan 805 ms · 11,312행 전량 필터. 누적 seq scan 3,153회 · 2,960만 행.
호출자가 **전부 학습자 화면**(`/text/[id]` · `/wordvault/browse` · 만화 · 딕테이션).
→ 표현식 인덱스 `((curation_query->>'book_id'))` 로 **교체**(순증 아님).

### E-4. 단건 UPDATE 52.8만회 + HOT 파괴

`csat_dcp_items.answer_key` 단건 PATCH **528,797회 · 총 10,998초(3시간)**.
부분 인덱스 `csat_dcp_items_missing_explanation_idx` 의 술어가 `answer_key` 를 참조해
**HOT update 가 깨진다** — UPDATE 533,478 중 **non-HOT 282,987**, 힙이 960 MB 여야 하는데 **1,289 MB**.
다만 그 인덱스는 8일 전 승인으로 만들어졌고(29,048 ms → 124 ms) 지금도 드레인이 쓴다(EXPLAIN 2.0 ms).
→ **퇴역 조건**: 해설 없는 문항이 0 이 되면 DROP(현재 **7,150 / 880,760 = 0.81% 남음**).
   `apps/web/src/lib/admin/help/csat.ts` 의 `drain`·`cautions` 에 적을 것.

### E-5. 인덱스 — 버릴 44개(36 MB) · 새로 만들 6개

- **DROP 44개 · 36 MB**: shared_dictionary 분류 스프린트 잔여 16개(20.2 MB, GIN 3개는 `@>`·`?` 소비자 0),
  topic_word_stats 2 · library_books 전문검색/trgm 4(`@@`·`textSearch(`·`similarity()` 호출 0건) ·
  word_frequency_stats 5 · 접두사 중복 8 등.
- **중복·포함 인덱스 13짝**(8짝은 위 44에 포함). 좁은 쪽이 실제로 쓰이는 5짝은 DROP 후 EXPLAIN 재확인 필수.
- **미보완 FK 52건 중 새 인덱스는 4개만** 제안 — 나머지 48건은 자식 표가 전부 ≤12 MB(대부분 8~40 kB)라
  쓰기 비용만 늘린다. 큰 표 FK 는 이미 부분 인덱스가 받는다.
- ⚠️ **처음 지목한 미사용 상위 4개는 전부 DROP 대상이 아니다**:
  `idx_lbv_word_lemma`(53 MB · 드레인 커서를 53,668 ms → 7,375 ms 로 줄인 측정치가 마이그레이션에 있음) ·
  `idx_shared_words_vocab_ref`(32 MB · FK 자식 SET NULL 유일 인덱스, 지우면 681,033행 풀스캔) ·
  `idx_lbv_lemma`(16 MB · 같은 이유) · `csat_dcp_items_missing_explanation_idx`(8일 전 생성 · 사용 중).
  **조사 중에 둘이 `idx_scan` 0 → 1 로 올라갔다. 0 은 죽음이 아니다.**

### E-7. RLS 가 행마다 auth.uid() 를 부른다

advisor `auth_rls_initplan` **69건**(직접 센 수와 일치). 그중 **7건은 고칠 게 아니라 지우는 것**이 맞다 —
`service_role` 은 `rolbypassrls = true` 라 정책과 무관하게 전부 보는데, `TO public USING (auth.jwt()->>'role'='service_role')`
정책이 **모든 행에서 auth.jwt() 를 호출**한다. 가장 큰 것이 `library_article_vocabularies` **34,061,777행**이다.
advisor 가 놓친 같은 결함이 **35건 더** 있다(맨몸 `is_admin()`·`is_admin_or_curator()`) — 별건으로 분리.
중복 정책은 150건 중 **16개를 제거 가능**(죽은 service_role 11 + 완전 포함 1 + OR 병합 5) → 150 → 133.
→ `_pending_rls_initplan.sql` (DB 원문을 읽어 기계적으로 감싸는 DO 블록 · 재실행 안전)

## 5. 갱신 배선이 없는 머티리얼라이즈드뷰
