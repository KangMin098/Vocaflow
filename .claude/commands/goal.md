# /goal — 자율 목표 달성 루프

## 목표

$ARGUMENTS

## 시작 전 단 하나의 확인

**목표가 숫자로 측정 가능한가.** 아니라면 루프가 돌지 않는다("좋게 만들어" ❌ / "커버리지 90%" ⭕).
숫자가 없으면 **먼저 측정 가능한 형태로 바꿔 제시하고** 그 정의로 진행한다 — 사용자에게 되묻느라
멈추지 않는다. 다만 그 재정의가 무엇인지는 첫 사이클 보고에 분명히 적는다.

기준이 외부 비교(“업계 수준 이상” 같은)라면 **그 수준을 먼저 실측해 숫자로 고정**한다.
근거 없이 정한 임계값은 목표가 아니라 짐작이다.

## 실행 규칙

아래 루프를 목표 달성 + 초과까지 스스로 반복한다. 중간에 멈추거나 확인을 요청하지 않는다.
**예외 — 반드시 먼저 묻는다:** 마이그레이션 적용 · 데이터 삭제/덮어쓰기 · 외부 발송 ·
`main` 푸시 · force push · `.env*` 커밋 · 30개 이상 파일 변경.

### 루프 (매 사이클)

1. **PLAN** — 현재 상태와 목표의 격차를 **측정**하고, 이번 사이클 작업을 1~3개로 쪼갠다.
   추정으로 격차를 적지 않는다. 모르면 먼저 잰다.
2. **DO** — 작업을 실행한다.
3. **TEST** — **반드시 실제로 실행해 검증한다.** 테스트가 없으면 먼저 만든다.
   타입체크·린트·빌드 통과 필수. "통과했을 것" 은 통과가 아니다.
4. **REVIEW** — 비판적으로 자기 검토: 엣지 케이스 · 성능 · 코드 품질 · 목표 기준 대비 수치.
   특히 **이번 변경이 다른 축을 깎지 않았는지** 본다(한 지표를 좋게 만들면 대개 다른 지표를 판다).
5. **EVALUATE** — 달성률을 %로 기록한다. 계산 근거(분자/분모)를 함께 적는다.
6. **IMPROVE** — 이번 사이클에서 발견한 문제를 다음 사이클 PLAN 에 반영한다.

### 종료 조건

- 목표 100% 달성 후 **한 사이클 더** 돌려 초과 개선(성능·품질·엣지케이스)을 시도한 뒤 종료.
- 같은 문제로 **3회 연속 실패** 시 접근법을 근본적으로 바꿔 재시도. 그래도 안 되면
  원인 분석 보고서를 쓰고 중단한다 — 숨기고 계속하지 않는다.

### 보고 형식 (매 사이클 끝)

```
[Cycle N] 달성률: XX%  (근거: 분자/분모)
✅ 완료: …
❌ 실패 / 발견된 문제: …
➡️ 다음 사이클: …
```

### 금지사항

- 테스트 없이 "됐다" 고 판단하기
- 목표 미달인데 종료하기
- 실패를 숨기거나 낙관적으로 보고하기
- **근거 없는 임계값을 목표로 삼기** — 기준선은 재서 정한다
- 측정하지 않은 개선을 개선이라고 적기

### 이 저장소에서 함께 지킬 것

- 코드 변경 시 관련 `docs/*.md` 를 같은 커밋에서 갱신 (CLAUDE.md §자동화 정책)
- Admin 화면·드레인 절차가 바뀌면 `lib/admin/help/*` 도 같은 커밋에서
- 커밋은 `git commit --only <파일 개별 지정>` — 워크스페이스를 여러 세션이 공유하므로
  디렉터리를 통째로 지정하면 남의 작업이 딸려 들어간다
- 논리적 milestone 마다 커밋·푸시 (작업 브랜치만)

## 턴 경계에 대하여

이 명령은 **한 번의 호출**을 자율 루프로 만든다. 도구 호출이 끝나면 그 턴도 끝나므로,
무인으로 여러 시간 반복하려면 `/loop` 로 걸어야 한다. 이 점을 사용자에게 사실대로 알린다 —
"계속 돌고 있다" 고 말하지 않는다.
