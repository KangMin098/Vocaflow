# /db-checkpoint — 위험 작업 앞뒤를 잰다

> **사후에는 알 수 없다.** 30일에 마이그레이션 184건이 들어가는 저장소에서 "이 변경이 무엇을
> 건드렸나" 는 앞에서 찍어 두지 않으면 영영 답이 없다. 2026-08-29 에 도서 274권을 대량 발행하면서
> 야간 배치가 죽었는데, 그 인과를 알아내는 데 이틀이 걸렸다 — **before 가 없었기 때문**이다.

## 언제 거는가

| 상황 | 왜 |
|---|---|
| 마이그레이션 적용 전 | 인덱스·제약·RLS 변경이 어느 축을 건드렸는지 |
| 대량 발행·대량 적재 전 | 용량과 야간 배치 비용이 선형으로 따라 오른다(발행 12권 → 312권이 그랬다) |
| 드레인 시작 전 | **쓰기 폭주가 여기서 난다.** 2026-09-06 장애의 원인이 드레인이었다 |
| `VACUUM FULL` · `REINDEX` 전 | 되돌릴 수 없고 락을 잡는다 |
| 인덱스 추가·삭제 전 | 미사용 인덱스를 지웠는데 실은 배치가 쓰고 있던 경우 |

**거는 비용은 몇 초다**(수집 1회). 안 걸어서 치르는 비용은 이틀이다.

## 절차

### before — 작업 시작 전

```sql
select record_db_health_checkpoint('<라벨>', 'before', '<무엇을 할 것인지 한 줄>');
```

라벨은 **나중에 이어 붙일 수 있는 이름**으로 짓는다 — 마이그레이션 번호(`20260906040000`),
드레인 이름(`dict-drain-4칸`), 발행 배치명. 같은 라벨을 다시 찍으면 덮어쓴다
(작업을 다시 시작하는 경우가 실제로 있고, 그때 옛 before 를 남겨 두면 비교가 거짓이 된다).

**before 를 찍기 전에 이 셋을 확인한다** — 찍는 것보다 이쪽이 중요하다:

1. **되돌릴 수 있는가.** 없으면 사용자에게 먼저 묻는다(`VACUUM FULL`·`DROP`·데이터 삭제).
2. **쓰기를 얼마나 만드는가.** 행 단위로 쓰는 루프면 **시작 전에 배치로 고친다.**
   초당 30건 넘는 단건 쓰기는 이 DB 를 멈춘다(실측 33건/초에서 25분 정지).
3. **지금 다른 세션이 무거운 일을 하고 있지 않은가.**
   `select count(*) filter (where state='active') from pg_stat_activity;`
   활성 연결이 평소보다 많으면 기다린다. 워크스페이스를 여러 세션이 공유한다.

### after — 작업이 끝난 뒤

```sql
select record_db_health_checkpoint('<라벨>', 'after', '<무엇을 했는지>');
select * from db_health_checkpoint_diff('<라벨>');
```

### diff 읽는 법

| status | 뜻 | 어떻게 할까 |
|---|---|---|
| `disappeared` | **가장 중요하다.** after 에 그 지표가 없다 = 그 축의 수집이 실패했다. 수집기는 축마다 예외를 삼키도록 만들어져 있어 함수는 성공으로 끝난다 | 그 축을 손으로 확인한다. 진짜 고장이면 critical |
| `appeared` | 없던 지표가 생겼다. 새 지표를 넣었거나 회전 표본이 다른 대상을 골랐거나 | 아래 양성 사례 참조 |
| `changed` | 값이 바뀌었다 | `pct` 가 큰 것부터 본다 |
| `same` | 안 바뀌었다 | 맨 뒤로 정렬돼 있다 |

⚠️ **알려진 양성(정상) 사례 — 이걸 모르면 매번 헛짚는다**:
`bloat_sampled_pct` 는 **회전 표본**이라 실행마다 다른 표를 잰다. 그래서 거의 항상
`disappeared` 1건 + `appeared` 1건이 함께 나온다(실측: `lexicon_clean` → `topic_corpus_queue`).
**둘의 `subject` 가 다르고 그 지표가 `bloat_sampled_pct` 뿐이면 정상이다.**

### list — 걸어 둔 체크포인트 보기

```sql
select label, phase, measured_at, note, created_at
from db_health_checkpoints order by created_at desc limit 20;
```

`before` 만 있고 `after` 가 없는 라벨은 **끝나지 않은 작업**이다. 오래된 것이 있으면
그 작업이 중단된 것인지 확인한다 — 열린 채로 두면 다음 사람이 그 before 를 믿고 비교한다.

## 하지 않을 것

- 체크포인트를 찍었다고 안전해지지 않는다. **찍는 것은 관측이지 보호가 아니다.**
  되돌릴 수 없는 작업은 여전히 사용자 승인이 필요하다.
- `after` 를 작업 **직후**에 찍어라. 몇 시간 뒤에 찍으면 그 사이 다른 세션의 변경이 섞이고,
  그러면 diff 는 인과가 아니라 그냥 시간차다.
- 라벨 없이 찍지 마라 — 함수가 거부한다. 라벨이 없으면 before 와 after 를 이을 수 없다.
