# FYM commercial textbook benchmark engine

This directory contains the **metadata-only** benchmark contract, distribution builder, F02 comparator, and stale checks. No commercial passage or item text is stored here. The currently tracked benchmark corpus is **N=0**; no production protocol or textbook sample is sealed. All test records are generated in memory and are synthetic fixtures.

Real intake requires two seals. `BENCHMARK_SELECTION_PROTOCOL` fixes search sources/cutoff, eligibility, selection algorithm, nine-axis codebook, missing-data and rater rules **without passage IDs** before difficulty analysis. Metadata screening then enumerates stable candidate IDs and hold/reject reasons without measuring the nine difficulty axes. `BENCHMARK_SAMPLE_MANIFEST` binds the first seal, inventory and screening snapshot hashes, selected/excluded IDs and cohort composition. Only then may nine-axis analysis and admission start. The current `validateProtocol` checks the final selected-ID protocol but does **not yet enforce this two-seal chain**. Do not treat a locally hashed file inventory or a synthetic fixture protocol as a real sealed benchmark.

## Input contract

`protocol.json` must have `schema=frym-benchmark/1`, `status=sealed`, a version, SHA-256 hashes of the codebook and selection manifest, and an embedded sealed `selection_manifest` whose `selected_sample_ids` and publisher/title `representative_editions` match `selection_manifest_hash`. `codebook_hash` must equal the canonical hash of the embedded `axes`. It must cover `elementary_5`, `elementary_6`, `middle_1`, `middle_2`, `middle_3`, `high_1`, `high_2`, `high_3` in that order. Each of the nine axes declares one primary metric, a `ratio` or `ordinal` scale, unit, measurement method, missing rule, rater policy, burden direction, measurement `resolution`, `minimum_meaningful_delta`, auxiliary metric list, auxiliary override rule, agreement floor, and missing priority. Ratio axes and type-specific item difficulty seal nonnegative `valid_min` and finite `valid_max`; ordinal axes declare ordered anchor levels. Supported auxiliary rules are `none` with an empty list and `veto_if_outside_p10_p90` with a nonempty list; other rules cannot be sealed. A reference shift below the sealed meaningful delta cannot establish a stable axis; an F02 shift below it cannot count as a match. The minimum, fit, and separation rules are validated by `validateProtocol`; a draft or altered seal fails closed. **The real codebook and selected IDs must be fixed before textbook difficulty measurements.**

Each metadata-only sample has `sample_id`, publisher, series, title, single grade, edition, publication year, difficulty step, ISBN (or publisher ID and canonical URL), passage ID, page, genre, source method and access date, rights basis, analyzer version and evidence locator, analysis/passage/item/scoring SHA-256 hashes, word and item counts, codebook/selection hashes, nine numeric measurements, per-axis agreement, item-type counts and type-specific difficulty. Digital URLs must be parseable canonical HTTP(S) URLs without fragments, and each publisher/title uses only the sealed representative edition. `analysis_hash` is the canonical `sampleAnalysisHash` of every sample field except `analysis_hash` itself, including grade, genre, length, item count, evidence location, measured metrics and ordinal review evidence. Ordinal measurements require distinct independent rater IDs with matching ratings, or an identified third adjudicator if they differ. `rights_basis=authorized_local_analysis` records an upstream rights decision; this engine does not grant permission. Missing items, multiple grade labels, unknown rights, unselected IDs, duplicate passages, missing axes and changed hashes are rejected. Rejections remain visible in the snapshot. Source text belongs in the authorized external store.

For a grade to be calibrated, the builder needs at least 30 eligible passages, three publishers, two series per publisher, publisher share at most 40%, series share at most 20%, at least 12 explanatory, 12 argumentative, six narrative passages, and at least six passages in each length bin (`<150`, `150–299`, `>=300` words). It computes `p10`, `p25`, median, `p75`, IQR, `p90` for every axis. If any grade is insufficient, the workflow stays `insufficient_benchmark`.

The F02 comparator requires the current F02 passage hashes, the **common** item and scoring-key hashes, current freeze hash, each variant's item IDs and count matched to the frozen 12-item packet, the same `codebook_hash`, and an `analysis_hash` equal to the canonical hash of the F02 input object without that field. It also requires an E3 batch verified by the existing cross-agent auditor. Its middle-1 and high-1 arms receive independent benchmark fit results. The fit comparison needs 12 genre/length-matched samples from three publishers per arm; all five core axes and seven of nine axes must lie inside reference p10–p90. Each F02 item type also needs at least the sealed number of comparable textbook samples; its type-specific difficulty **and item share** must fit. A missing type yields `MISSING_ITEM_TYPE`; a type mismatch fails target fit even when seven other axes pass. The item primary metric alone follows the seven-of-nine rule when all types are comparable. Separation compares direction and magnitude only within a common genre/length range and leaves out each publisher in turn to check direction stability, allowing machine-precision error at a sealed change threshold. It returns `pass`, `fail`, `inconclusive`, or `insufficient_benchmark`; definite failures take precedence over sample shortages. It can mark `gold_s_candidate`; it **never grants Gold-S or DB seed**.

## Commands

```text
node scripts/textbook/frym-benchmark/benchmark-run.mjs build <sealed-protocol.json> <metadata-samples.json> <new-snapshot.json>
node scripts/textbook/frym-benchmark/benchmark-run.mjs verify <sealed-protocol.json> <snapshot.json>
node scripts/textbook/frym-benchmark/benchmark-run.mjs judge <sealed-protocol.json> <snapshot.json> <metadata-samples.json> <f02-input.json> <verified-e3-batch-dir> <new-decision.json>
node scripts/textbook/frym-benchmark/benchmark-run.mjs verify-decision <sealed-protocol.json> <snapshot.json> <f02-input.json> <verified-e3-batch-dir> <decision.json>
```

`build` and `judge` use exclusive-create output: a rerun cannot overwrite the earlier snapshot or decision. Use a new revision path. `verify` and `verify-decision` are read-only and repeatable. `judge` rechecks the active F02 seal, the four passing human review files via `check-f02-freeze.mjs`, and the **actual 28/28 E3 batch directory** with `verifyStage` before accepting an E3 claim. It binds the decision to a byte digest of files in the E3 batch and its Stage A/B audit directories; `verify-decision` recomputes that digest and rechecks the F02 review freeze. These local hashes are not publisher or model-provider attestations. `verify-decision` returns `STALE` and exit 1 if the version, benchmark snapshot, F02 input, review evidence, E3 run, or its audit evidence changes. A changed sample measurement fails comparison against the sealed snapshot.

`workflowState` exposes `draft → sealed → insufficient_benchmark | benchmark_calibrated → fail | inconclusive | gold_s_candidate | stale`. It never returns Gold-S or a seed-eligible state. A benchmark revision starts again at a new sealed protocol; prior decisions are preserved and become stale when checked against that version.

Run the synthetic regression suite with `node --test scripts/textbook/frym-benchmark/benchmark.test.mjs`. It does not read the commercial corpus or write to the database.

## Pre-intake pipeline status

`status-admitted` is a read-only, metadata-only check across current admission, admitted snapshot, and optional benchmark decision:

```text
node scripts/textbook/frym-benchmark/benchmark-run.mjs status-admitted <sealed-protocol.json> <local-candidates.json> <metadata-samples.json> <admission-audit.json> <receipt.json> <snapshot-or-dash> <f02-or-dash> <e3-dir-or-dash> <decision-or-dash>
```

Use `-` for each not-yet-created downstream artifact. Candidate JSON stays outside the repository. The check recomputes admission against current source bytes; `admission-hold` or `admission-reject` stops there. An all-pass admission without a snapshot reports `admission-pass`. A present snapshot must be sealed to the same receipt and rebuilt against current samples; missing grade coverage reports `insufficient_benchmark`. A decision requires the current F02 freeze, the 28/28 E3 batch and Stage A/B source records, its recorded 81/81 Stage C gate, and recomputation of the benchmark result. Status checks read the recorded Stage C result without rerunning mutation tests or writing files; the dedicated E3 verifier still replays Stage C. Missing or mismatched evidence reports `decision-unverified` or `stale` with a nonzero exit code. Other read-only states are `benchmark_calibrated`, `fail`, `inconclusive`, `evaluated_not_candidate`, and `gold_s_candidate`.

`gold_s_candidate` is only a benchmark decision status. Every pipeline status output keeps `gold_s=false`, `seed_eligible=false`, and `db_seed=false`. Gold-S certification and seed eligibility have separate authority and operating gates. Hold/reject needs corrected candidate evidence in a new output revision. Stale source, protocol, receipt, snapshot, F02, or E3 evidence requires a new revision and re-evaluation; the previous artifact remains for audit. No real benchmark corpus has been admitted.

The status output also contains a `promotion` preview. Only a decision recomputed as a current `gold_s_candidate` **in the same process** can become `ready_for_owner_review`; a serialized status JSON supplied later cannot reproduce this proof. The preview binds benchmark version, admission receipt, snapshot and decision hashes into `review_evidence_hash`. This is a review packet identity, not an approval signature. Any missing, stale or mixed evidence blocks review. Even when review-ready, `gold_s=false` and `seed_eligible=false`: an issued owner certificate must be bound to the current decision, and the separate seed path rechecks current rights, provenance, content hashes and review status before any DB write. The status command does not issue a certificate or open seed eligibility.

## Gold-S certification contract

`assessGoldSContract` is a read-only preflight, not a certificate issuer. It accepts only a same-process verified candidate and checks a real-commercial-textbook corpus declaration with positive admitted count, distribution hash, benchmark version, snapshot hash and admission receipt hash. A synthetic fixture or zero real distribution stays `hold`. The owner review must bind the preview's `review_evidence_hash`, current decision hash, distribution hash and benchmark version, with explicit `approve`, owner ID, decision time, rationale, revision and canonical review hash. A rejected benchmark or owner decision is `reject`; changed pipeline or review evidence is `stale`; absent/incomplete evidence is `hold`. A structurally complete packet is only `reviewable`: the local fields and hash do **not** authenticate the owner or prove that a declared corpus is commercial. `inspectGoldSCertificate` read-only checks a separately issued certificate against current review, decision, distribution, receipt, snapshot, content and rights hashes; it requires a valid issuer signature over the exact certificate bytes. Missing authority is `unverified`, changed evidence is `stale`, and revoked certification or lost rights is `invalidated`. Any source, admission, protocol, codebook, F02 or E3 revision must first recompute the bound decision and review evidence before this check; a caller must never reuse a saved current-state JSON. Certification never implies seed eligibility; a separate gate rechecks current rights, provenance, content hashes and operational review before DB write authorization. The signed seed path is implemented, but no production certificate has been issued; real corpus N=0, Gold-S=0 and DB seed=0.

`issueGoldSCertificate` now provides an in-process issuance path after preflight. It requires separate Ed25519 signatures on the exact corpus declaration and owner review, verified with independently pinned curator and owner public keys whose IDs match the signed records, plus current permitted rights/content hashes and an injected issuer private key. The curator must verify the underlying commercial source and distribution before signing; the local declaration alone cannot prove them. No keys are read from the repository, and no production keys or authenticated real corpus are configured here. The issuer signs the bound certificate; `inspectGoldSCertificate` checks that signature against a pinned issuer public key and issuer ID instead of accepting a caller-supplied `verified` flag. Synthetic tests use ephemeral keys only. A changed bound hash is `stale`, revoked certificate or lost rights is `invalidated`; Gold-S never implies seed eligibility or a DB write. The current real corpus, issued Gold-S and DB seed remain zero.

## Seed eligibility boundary

`previewSeedEligibility` checks the freshly verified candidate, signed Gold-S certificate and an operational packet bound to that certificate, decision, rights/content hashes, provenance and item set. Missing, changed or mixed evidence is `blocked`. A complete packet is only `ready_for_seed_review`, with `seed_eligible=false` and `db_seed=false`. Its local packet hash does not authenticate the operational reviewer or independently re-read DB rights. The signed eligibility gate still requires source/rights to be freshly rechecked by its caller before authorization. A seed-eligible decision would still not mean a DB write occurred. The actual corpus, Gold-S and seed counts remain zero.

`issueSeedEligibility` is the separate authorization contract. It requires a signed operational packet from a pinned reviewer and a signed approval over the preview evidence hash from a different pinned approver; an injected issuer key signs the eligibility decision. Reviewer, approver and issuer IDs and public keys must be distinct. `inspectSeedEligibility` verifies its issuer signature against a pinned key and rechecks the current packet. Its `current` result means only seed eligibility, **never** that a DB write occurred. Callers must independently recompute the current source and rights state before invoking it, and must not use a saved status JSON. The alternative `--gold-s-seed` DB importer path is implemented, but no production identity registry, keys or real corpus is configured. The test suite exercises signatures with ephemeral synthetic keys; actual Gold-S, seed eligibility and DB seed remain zero.

## Adapted article DB admission

`adapt-drain-import.mjs --target <target.json> --gold-s-seed <bundle.json> --gold-s-policy <external-policy.json>` is the alternative to the existing student-v2 `--educational-validation` path. The bundle is `{ "schema": "frym-gold-s-seed-bundle/1", "entries": [{ "source_id": "<source UUID>", "target_key": "<target key>", "passage_hash": "<SHA256>", "certificate": {}, "eligibility": {} }] }`. The operator-managed policy must remain outside the repository. Both the path parent and the existing policy file are resolved before reading, so an external file symlink into the repository is rejected. It pins Gold-S and seed issuer IDs and PEM public keys, each key's `valid_from`/`valid_until`, maximum certificate ages in days, and revoked certificate hashes, eligibility hashes and issuer IDs. This is a trusted local policy file, not a provider attestation or a self-authenticating hash. A key rotation adds a new issuer ID and key while retaining the old entry only for its explicitly allowed validation window. Removing or revoking the old entry invalidates its certificates. The importer checks both issuer signatures, current policy, exact source/target/passage and current source rights hash in dry-run and immediately before `--commit` inserts. After the final recheck it reports excluded counts and reasons separately from the initial dry-run summary. It also rejects a policy revision during a commit run and records the policy hash with the metadata-only `provenance.gold_s` summary on a queued child. Existing source rights, adaptation and agent-review checks remain in force. The bundle must originate from the fresh benchmark and signed-approval process; a self-declared JSON is insufficient. No real bundle or trusted operational policy is configured, so DB seed remains zero.

Policy shape: `{ "schema":"frym-gold-s-operational-policy/1", "revision":"r1", "gold_issuers":[{"id":"...","public_key":"-----BEGIN PUBLIC KEY-----...","valid_from":"2026-10-01T00:00:00Z","valid_until":"2026-11-01T00:00:00Z"}], "seed_issuers":[...], "gold_max_age_days":30, "seed_max_age_days":7, "revoked":{"certificate_hashes":[],"eligibility_hashes":[],"issuer_ids":[]} }`. The dates and age values here illustrate the schema; an operator must choose real windows before issuing certificates. Every policy change requires a new revision and a new import dry-run. A missing/invalid policy, expired certificate, inactive key or revoked hash/issuer blocks DB admission. Certificate age and key windows are evaluated with the run's current UTC time, so a dry-run pass never guarantees a later commit pass.

The DB has a live `UNIQUE (source, source_id)` constraint on `library_articles`. The importer also checks existing children and rechecks the source and policy before each insert batch. Gold-S `--commit` additionally requires `--gold-s-audit <new-external-audit.jsonl>`; exclusive creation prevents overwriting an earlier attempt. The journal records a run ID, policy and bundle hashes, candidate count, each batch's source IDs before and after insert, and a hash chain. It contains no source text, questions, credentials, PEM keys or full signed artifacts. A missing `run_complete` means the run was interrupted; `node scripts/textbook/frym-benchmark/seed-audit-run.mjs <audit.jsonl>` checks local journal integrity and reports pending batches. A truncated final record returns `invalid_tail` with the verified prefix and pending batches; inspect DB rows by source ID before rerunning with a new journal path. Never append to or reuse the damaged journal. The hash chain detects accidental edits but is not an external attestation; preserve the original file in the operator's protected archive. Reconcile the listed `(source, source_id)` keys against DB rows, then rerun dry-run and commit with a **new** audit path: existing child IDs are skipped and remaining candidates are revalidated. Do not upsert over an existing child or treat a duplicate-key error as proof that the submitted certificate was accepted. Gold-S children are inserted as `queued`; generic ACP `process-queue` excludes all `reading:` source IDs, and downstream item export selects only `ready` and `published` rows. A separate promotion gate must recheck the current policy and source before a queued child moves to `ready`; the import receipt alone does not authorize that later transition.

The import gate also requires the certificate's owner, curator, issuer, decision, distribution, review, receipt and snapshot fields, and the eligibility record's operations reviewer, approver and issuer fields. A correctly signed but incomplete artifact is rejected. Gold-S issuance requires separate curator, owner and issuer identities and keys; seed eligibility issuance requires separate operations reviewer, approver and issuer identities and keys. These structural checks are independent of the issuer-signature check and remain active in both dry-run and pre-insert rechecks.

## Local file admission adapter

`local-admission-run.mjs` is the metadata-only bridge ahead of `benchmark-run.mjs`; it does not alter the benchmark decision engine. It reads local source files only to identify format and calculate SHA-256. The original files are never copied or rewritten. It accepts an **external, locally stored** candidate JSON array whose entries contain `source_path`, `expected_file_hash`, bibliographic `metadata`, reviewed `extraction`, and a separate 9-axis `analysis`. The CLI requires candidate JSON and raw extracted text outside the repository; only the metadata output and audit may be retained. Neither output contains the source path, passage text, item stems, or answers.

The optional `local-draft-run.mjs` bridge reads the existing `textbook-corpus/extract.mjs` `meta.json` and `pages.jsonl` (or a compatible external converter result) and produces one **held page candidate** per nonempty page. Empty pages are listed in `held_empty_pages` without blocking other pages. It checks the extractor's SHA-1 `sourceHash` against the original file and records a new SHA-256 file hash. It never treats the whole page as a passage or infers question boundaries. The local draft includes raw page text for review, so its output path must be **outside this repository**. HWP artificial chunks, stale extraction, unknown OCR mode, duplicate page IDs and unsupported formats fail closed. For EPUB/DOCX/images, a separate converter must provide the page-bound `meta.json`/`pages.jsonl` and explicit method/OCR mode; format identification alone cannot extract text.

```text
node scripts/textbook/frym-benchmark/local-draft-run.mjs draft <local-source-file> <extractor-meta.json> <pages.jsonl> <metadata-hints.json> <new-local-candidates.json>
```

The reviewer then fills publisher/edition and single-grade evidence, separates passage and questions from `review_material.page_text`, confirms both boundaries, and supplies the separate sealed-codebook analysis tied to passage/item/key hashes. Only then run `prepare` below. Page drafts are deliberately inadmissible until those steps are complete.

```text
node scripts/textbook/frym-benchmark/local-admission-run.mjs dry-run <sealed-protocol.json> <local-candidates.json>
node scripts/textbook/frym-benchmark/local-admission-run.mjs prepare <sealed-protocol.json> <local-candidates.json> <new-metadata-samples.json> <new-admission-audit.json> <new-receipt.json>
node scripts/textbook/frym-benchmark/local-admission-run.mjs verify <sealed-protocol.json> <local-candidates.json> <metadata-samples.json> <admission-audit.json> <receipt.json>
node scripts/textbook/frym-benchmark/benchmark-run.mjs build-admitted <sealed-protocol.json> <local-candidates.json> <metadata-samples.json> <admission-audit.json> <receipt.json> <new-snapshot.json>
node scripts/textbook/frym-benchmark/benchmark-run.mjs verify-admitted <sealed-protocol.json> <snapshot.json> <local-candidates.json> <metadata-samples.json> <admission-audit.json> <receipt.json>
```

`dry-run` reads candidates and local files without writing. `prepare` exclusively creates passing metadata, an audit of all held/rejected candidates, and a receipt binding canonical candidate input, metadata, audit, benchmark version, protocol, codebook and selection hashes. Aggregate state is reject if any candidate rejects, otherwise hold if any holds or the list is empty, otherwise pass. Only a current all-pass receipt is build-ready. `verify` recomputes admission from current files and reports stale on source, candidate, metadata, audit, receipt or protocol changes. New evidence requires a new output revision; old artifacts stay intact. These are local hashes, not publisher attestations.

`build-admitted` creates a sealed snapshot envelope containing the existing engine snapshot plus `admission_receipt_hash`; `verify-admitted` checks both and rebuilds against current samples. `judge-admitted` and `verify-decision-admitted` insert `<local-candidates> <metadata-samples> <admission-audit> <receipt>` after snapshot in the corresponding base command; the decision binds the same receipt. Direct `build`/`judge`/`verify` are for non-file synthetic fixtures; direct `verify` rejects an admitted envelope. An old bare snapshot must be rebuilt as a new revision; it cannot be promoted by supplying a receipt later. Candidate JSON must remain outside the repository in all commands. The source hash, selected sample ID, representative edition, grade, rights decision, passage and question boundaries, OCR verification, item keys, nine metrics, independent-rater agreement and codebook must pass. The audit includes `sample_id_hash` so a selected but non-opaque ID can still be matched without copying it into audit text. `evidence_locator` is an opaque identifier such as `analysis:sample_1`, never a local path. File edits cause `SOURCE_HASH_CHANGED`; uncertain boundaries cause `NEEDS_MANUAL_ADMISSION`; missing analysis causes `NINE_AXIS_ANALYSIS_MISSING`. Whitespace/NFC-equivalent duplicate passages are all excluded. A benchmark protocol change requires a new output revision. No real benchmark protocol or corpus has been sealed or admitted.

Candidate structure (illustrative keys only; values must be real reviewed evidence):

```json
{
  "source_path": "<absolute local path, never in committed output>",
  "expected_file_hash": "<sha256 of original file>",
  "metadata": { "sample_id": "...", "publisher": "...", "series": "...", "title": "...", "grade": "middle_1", "edition": "...", "publication_year": 2026, "difficulty_step": "...", "ISBN": "...", "passage_id": "...", "page": "12", "genre": "expository", "rights_basis": "authorized_local_analysis", "access_date": "2026-10-06" },
  "extraction": { "method": "pdftotext_or_reviewed_ocr", "ocr_used": false, "source_file_hash": "<same original file sha256>", "page_range": "12", "passage_id": "...", "boundary_confirmed": true, "question_boundary_confirmed": true, "passage_text": "<local-only text>", "questions": [{ "id": "Q1", "stem": "<local-only text>", "type": "literal", "answer": "<local-only key>" }] },
  "analysis": { "codebook_hash": "...", "passage_hash": "...", "item_set_hash": "...", "scoring_key_hash": "...", "analyzer_version": "...", "evidence_locator": "...", "metrics": { "lexical": 0 }, "axis_agreement": { "lexical": 1 }, "item_type_difficulty": { "literal": 0 } }
}
```

All nine metric keys and all fields required by `screenSample` are required in practice; the short illustration is intentionally **not** admissible. The existing `scripts/textbook-corpus/extract.mjs` can supply page text from PDF, HTML/TXT and HWP, but its page output alone does not establish passage or question boundaries. HWP's artificial chunks do not qualify as page-bound drafts. It does not extract EPUB, DOCX or image text in this environment. For those formats, use an external reviewed converter/OCR result in the local candidate; `identifyLocalFile` can still hash and identify the original. `ocr_used` must be explicitly true or false; OCR and image extraction need `ocr_verified=true`. A file extension/signature match identifies a container, not its contents or edition. No automatic filename-based publisher/grade inference is admission evidence. The existing corpus readability analyzer is not a complete nine-axis analyzer; the separate analysis record must use the sealed codebook. Run synthetic adapter tests with `node --test scripts/textbook/frym-benchmark/local-draft.test.mjs scripts/textbook/frym-benchmark/local-admission.test.mjs`.
